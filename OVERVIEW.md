## Recent changes (last 10)

940. ✅ Shopware sync: **shop-eligibility gate + full product data + visibility** (live-test fixes). (1) **Gate:** unreviewed/non-shop items were landing in Shopware — the snapshot now computes `shopEligible = Shopartikel=1 AND agentically approved` (same approval as the ERP gate; scalar subselects so multi-run refs don't corrupt the stock SUM). Ineligible → **deactivated** if it exists (`active:false`), else **skipped**; never published. (2) **published→active:** `Veröffentlicht_Status='yes'` maps to product `active`. (3) **Full data:** the update path PATCHed stock only — now a shared `buildProductFields` writes name/description/price(net from tax, sales-channel currency)/active/stock on create AND update (specs/properties already worked). (4) **Visibility:** create now sets `visibilities:[{salesChannelId,visibility:30}]` (channel resolved once via `resolveSalesChannel` by accessKey → id+currencyId) so a published+active product actually appears in the storefront. `ShopwareUpsertResult.action` gained `deactivated`/`skipped`. Verified 10/10 gate + 3/3 property. Deferred: items without agentic approval never sync (matches ERP gate); pre-existing skeletons self-correct only on next enqueue; visibility on create only; images P3. → [erp-sync]
939. ✅ Fix Shopware create-product 500: `resolveCurrencyId` filtered `/api/search/currency` on `isSystemDefault`, a **runtime field** Shopware rejects in a criteria (`FRAMEWORK__RUNTIME_FIELD_IN_CRITERIA`). Only bit the **create** path (updates just PATCH stock), so ~half the items synced before the first new product wedged all further new-product syncs (500=retryable). Now resolves currency from the **sales channel** (`/api/search/sales-channel` filtered on `accessKey`, a real field) → its `currencyId` (correct per-channel, e.g. CHF for a Swiss shop); falls back to the seeded system-default currency id **uncached** so a transient failure can't pin the wrong currency. Failed jobs retry to success after redeploy. Verified 17/17. → [erp-sync]
938. ✅ Shopware **property sync** (P2a): Langtext/Spezifikationen → **filterable properties**. Operator insight: use Shopware property groups+options (native storefront filters), not custom fields. Each structured Langtext entry (`Record<string,string|string[]>`, keys `Prozessor`/`Display`/`Anschlüsse`/…) maps to a property group → option(s). `ShopwareAdminClient.upsertProductStock`→`upsertProduct` now also `syncProductProperties`: `ensurePropertyGroup` (create `filterable:true` if missing) + `ensurePropertyOption` (both cached across jobs), then reconciles the product's associations to **exactly** the desired options — robust to either Shopware write semantic (PATCH full desired list, then 404-tolerant DELETE of stale links); array values → multiple options. The DB snapshot now parses `item_refs.Langtext` and passes the object form as `properties` (freeform prose → none). Property errors share the retry classification; stock is set first so a property hiccup never loses stock, and retries are idempotent. Verified: P1 suite 15/15 post-rename + new property cases (create/link/remove-stale, array→2 options under reused group). Deferred: contract-driven curation of which keys are filterable; translations/units/position. → [erp-sync]
937. ✅ Shopware **stock sync live** (P1): direct-to-Shopware, create-if-missing, absolute stock. New Admin-API write client (`backend/shopware/adminClient.ts`) resolves a product by `productNumber`, `PATCH`es absolute `stock` if it exists, else **creates** it (name/number/price + resolved-or-configured tax & currency, net computed from the rate) and the id is persisted back to `item_refs.ShopwareProductId`. The dispatch client (`syncClient.ts`) maps a queue job → DB snapshot (`getShopwareSyncSnapshotForPayload`: summed on-hand stock across instances; resolves Artikel_Nummer from itemUUID for move/stock jobs) → `upsertProductStock`, classifying 4xx as terminal and network/408/429/5xx as retryable; a deleted reference drains as success. The worker (`processShopwareQueue`) is now **started** in `server.ts` on a 10s reentrancy-guarded interval when `SHOPWARE_SYNC_ENABLED` + config ready (replacing the old "not implemented" reminder; also awaited its DB status-transition calls). Every job type converges to one idempotent op, so a missed/duplicated job self-heals. Optional `SHOPWARE_DEFAULT_TAX_ID`/`SHOPWARE_DEFAULT_CURRENCY_ID`. Verified via mock-fetch 15/15 (update/create/tax-pick/net/token-cache + skip/persist/retry-class). Deferred: queue retention, sales-channel visibility on create, richer product data (P2+). → [erp-sync]
936. ✅ Shopware config/env **cleanup** (P0) — one config, two working auth modes, leak fixed. Collapsed the two overlapping Shopware config systems into a single source (`backend/config.ts` `SHOPWARE_CONFIG`); the agentic tool (`agentic/tools/shopware.ts`) now consumes it and the duplicate block in `agentic/config.ts` is gone (so search action + agentic path finally agree on when Shopware is "on", both gated by `SHOPWARE_ENABLED`). **Made API-key auth actually work:** `ShopwareClient` accepted only client credentials and silently ignored `SHOPWARE_ACCESS_TOKEN`; it now authenticates with **either** a static access token **or** client credentials (`getToken` short-circuits on a token). Renamed the misleading `SHOPWARE_SALES_CHANNEL_ID` → `SHOPWARE_SALES_CHANNEL_ACCESS_KEY` (it's the `sw-access-key`, not a UUID; old names kept as deprecated aliases). Retired dead vars `SHOPWARE_API_BASE_URL`, `SHOPWARE_QUEUE_POLL_INTERVAL_MS`, `SHOPWARE_QUEUE_ENABLED`. **Fixed the queue leak:** `enqueueShopwareSyncJob` now no-ops unless `SHOPWARE_SYNC_ENABLED` (was writing a row on every `persistItem` with nothing draining it). Reconciled `.env.example`, `setup.md`, `ENVIRONMENT.md`, the runbook, and the module README. Verified: full grep sweep clean, all modules esbuild-resolve, client runtime 5/5 (incl. the new API-key path + constructor guard). → [erp-sync]
935. ✅ Added an admin Shopware **connection check** + status card — the first slice of the Shopware admin surface. `GET /api/admin/shopware/status` returns a secret-free config summary (enabled, base URL, sales-channel present, credential mode, config issues, whether a live check is even supported) plus `shopware_sync_queue` depth counts; `POST /api/admin/shopware/check` actively probes the two auth surfaces the read path needs — admin OAuth (`/api/oauth/token`) then store-api search — reporting per-step ok/HTTP-status/latency so a failure is attributable to admin creds vs. sales-channel key vs. reachability (`ShopwareClient.checkConnection`). New `ShopwareStatusCard` renders it on the Admin page (both admin endpoints gated by `ADMIN_SECRET`). The queue-depth panel doubles as the "watch jobs pile up" inspector, making the still-unimplemented dispatcher visible. Surfaced a real config finding in passing: the search client requires `CLIENT_ID`+`CLIENT_SECRET` and never uses `SHOPWARE_ACCESS_TOKEN`, so an access-token-only setup can't drive a check — the endpoint says so explicitly. Logic verified via mock-fetch (9/9 assertions); a harness-style test is in-repo (ignored like the other shopware tests per the pre-existing harness gap, todo #52). → [erp-sync]
934. ✅ Audited the Shopware integration and wrote an extension plan (`docs/PLANNING_shopware_integration.md` + shareable artifact). Findings: the **read** path (Store-API product search at `/api/shopware/search`, plus the agentic enrichment shortcut) works and is unit-tested, but the **write** path has never run — inventory mutations are enqueued into `shopware_sync_queue` yet `queueClient.dispatchJob()` is a stub that throws and the worker is not registered in `server.ts`. Only the Store API exists; every goal (stock sync, Langtext→custom fields, docs, images, quality/CO₂ badges, accessory cross-links) needs the unwritten **Admin API** + a mapping layer. Flagged a latent prod bug: `enqueueShopwareSyncJob` fires on every `persistItem` with no config gate and nothing drains/trims the table → unbounded growth. Surfaced the gating decision (direct-to-Shopware vs. ERP-mediated, since images already flow ERP→WebDAV today). No behaviour changed. → [erp-sync]
933. ✅ Operators can now delete a stored search-result link from an item's KI tab so a bad hit stops poisoning the reuse/grounding pipeline. The `Suchergebnisse (N)` list (search evidence surfaced in #916) was read-only; each link now has a remove control that calls a new `POST /api/item-refs/:id/agentic/search-links/delete` endpoint. Backend service `removeAgenticSearchLink` prunes the URL from `LastSearchLinksJson` (empties persist as `null` = "no evidence") and echoes the run's current Status/ReviewState back through `updateAgenticRunStatus` so only the links change — the run is *not* reset (unlike `deleteAgenticRun`). Logs an `AgenticSearchLinkRemoved` event. → [agentic]
932. ✅ Root-caused "most/all agentic runs fail with EXTRACTION_FAILED": the model returned **empty** completions because (a) the Ollama client set no `num_ctx` (default 2048) so the ~6-7k-token extraction prompt was silently left-truncated, and (b) extraction alone was fed the **raw, unbounded** search blob (16k+ chars for one item) — the sanitizer that shrinks the categorizer's context never ran on it. Fix: `MODEL_NUM_CTX` (default 8192) + optional `MODEL_FORMAT_JSON` on the Ollama client; a new deterministic `condenseSearchText` that keeps spec-bearing lines within a 12k-char budget instead of blindly truncating; and traceability — the blind `json match missing` debug line is now a `warn` with `rawLength`/`hadThinkBlock`/snippet, and the terminal error records `EMPTY_OR_NO_JSON` instead of a null reason. → [agentic]
931. ✅ Admin "Backup" is now a complete, restorable snapshot that never depends on env config. The button routed to `/api/export/items?mode=backup`, which (a) emits only items+boxes — no agentic runs, no events — and (b) resolved Langtext format via `LANGTEXT_EXPORT_FORMAT`, so setting that env to `html` (for ERP) silently made *backups* emit HTML cells that break on re-import. Now: Backup routes to `/api/export/data?format=zip&entities=items,boxes,agentic,events&mode=backup` (the four CSVs the importer already ingests); backup Langtext is **always** JSON (env override confined to the ERP boundary); backup is never row-capped (was truncating agentic/events at 500). Also fixed three latent bugs in `export-data` that made its boxes/agentic/events queries throw against the real schema (unquoted CamelCase identifiers) and added `LastSearchLinksJson` to the agentic export so search evidence survives restore. → [erp-sync]
