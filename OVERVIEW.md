## Recent changes (last 10)

1065. ✅ **KI cockpit — findings examples + coverage headline (easy wins).** A cluster said "Unerwünschter Text · 42" but not *which* text. Each cluster's drill-down now shows up to 5 distinct **examples** (the finding's `evidence`, else its message) — the concrete "what to adjust" — and the findings panel leads with a **coverage headline** ("N von M Läufen haben offene Befunde", pain #5). Both from the data already aggregated: `FindingCluster.examples` + `itemsWithFindings` in `aggregateRunFindings`, no new source. (Auto-drafting standards *rules* from these deterministic findings was considered and rejected — a new rule's real signal is reviewer rejections, not an existing rule firing.) 1217 pass; tsc clean. → [agentic]
1064. ✅ **KI cockpit increment 2 — pipeline behaviour chart + findings aggregation.** The cockpit now answers "overview / find bad items / manage at scale" (operator pains #5/#2/#1). A **status-distribution bar chart** (reserved status tokens, always labelled) shows how work sits across the pipeline (notStarted→queued→running→review→approved/auto→failed). **Open findings are aggregated into classes** — grouped by `type × field × subcategory` from the stored per-run `FindingsJson` (one cheap scan, no per-item recompute) — worst-first, each class drillable to its article numbers and with a bounded **"Überarbeiten (max 25)"** cohort-rework lever (targeted field rework via the restart path; queue cap paces it). Backend `aggregateRunFindings` (pure, unit-tested) + `getPipelineFindingsAggregate` + `GET /api/agentic/cockpit/findings` + `listRunsForFindingsAggregation`. 1216+ pass; tsc clean. → [agentic]
1063. ✅ **KI cockpit at `/ki` — pipeline control, not an item list (realignment).** Slice 3 (#1062) built `/ki` as the item list in disguise — wrong: the cockpit's job is to *manage data quality across the pipeline*, aggregate levers not per-row browsing. Reverted the `ItemListPage` `variant` hack; `/ki` now renders a real `PipelineCockpit`. **Increment 1 — the levers strip:** global auto-flags (`AUTO_APPROVE/REWORK/REVIEW`) are now **runtime-toggleable and persisted** (new `system_settings` keys, hydrated into the live config objects at startup, env seeds first boot only — the dispatcher already reads them live each tick), plus the auto-dispatch switch and a sweep-now button, over a health readout (queue occupancy + self-heal backlog by action/status). New `GET /api/agentic/cockpit` (operator) + `POST /api/admin/agentic-flags` (admin); `getPipelineCockpit()`/`setAgenticFlag()`/`hydrateAgenticFlagsFromSettings()`. Increment 2 = the findings-aggregation table ("what's systematically wrong"). 1216 pass; tsc clean. → [agentic]
1062. ✅ **Standalone KI-Läufe workbench (`/ki`) — KI-Runs surface, slice 3.** The deferred standalone page: the KI work is no longer trapped in a per-item tab. New `/ki` route + nav icon (agentic-gated) renders the `ItemListPage` shell in a new `variant="ki"` — same inventory, filters and bulk actions seen through an AI lens: a KI heading/intro, the Ki-Status column forced on, and "Review" filterable as the shared work queue (not keyed to who enrolled an item). No fork, no new data source — one component keeps the two lists in lockstep. Deeper KI columns (grade/findings) need list-payload backend work (next slice). 1216 pass; tsc clean. → [ui]
1061. ✅ **Bulk "Prüfen" — on-demand re-check routed through restart.** The sweep is (correctly) inert on non-stale data, but the operator wanted to force checks now. Added a "Prüfen" bulk action that re-runs the selected items cheaply (`validateOnly`, no LLM). The catch: `/api/agentic/run` is create-only and *skips* items that already have a run — exactly the review/approved set we want to re-check ("leaving it untouched, status: review"). So the trigger now POSTs the restart endpoint (`/api/item-refs/:nr/agentic/restart`, which re-runs any status) with `{ validateOnly: true, actor }`; restart action now reads and forwards `validateOnly`. Routes only — the auto-approve gate still decides approve vs. review. 1216 pass; tsc clean. → [ui]
1060. ✅ **KI tab → structured run detail (KI-Runs surface, slice 2).** The tab was one long pile (status + findings + diff + transcript stacked — the "crammed one tab" complaint). Now the summary stays pinned (actions + severity-coloured verdict + grade) and the detail panels sit one-at-a-time behind a sub-tab bar: Status · Zu prüfen (open-count badge) · Änderungen · Transkript. Opens on "Zu prüfen" when there's something to review. Same components, layout only; prefigures the standalone KI-Runs run-detail view. 1216 pass; tsc clean. → [ui]
1059. 🐞 **FIX: run target dropped the category → self-heal death loop + good items wrongly in review.** One item burned millions of tokens looping; many complete+clean items landed in review reading "5/5 · keine offenen Punkte". Single cause: `buildTargetFromRow` omitted `Unterkategorien_A`, so the run's `subcategoryCode` was null → no contract → `SpecContractVersion` stamped null AND the grade computed null. So a rework could never become non-stale (sweep re-picked it forever) and a validate-only item graded null at the auto-approve gate → review. Fix: the target now carries the category (coerced to number); a full run's categorizer still overwrites it. Belt-and-braces: a 30-min self-heal cooldown bounds any future loop. 1216 pass; tsc clean. → [agentic]
1058. ✅ **Auto-approve conservatism — data-quality floor + sweep respects the queue cap.** Operator saw an item auto-approved reading "Datenqualität 3/5 · 2 Pflichtfelder fehlen". That one is a *staleness artifact* (approved under a looser contract, then fields became required; the self-heal reworks it) — the gate never approves *with* block findings. But the principle needed teeth: auto-approve now also requires a grade floor — supervised runs ≥ `AUTO_APPROVE_MIN_GRADE` (4), validate-only (no supervisor) must hit grade 5, null grade never. And the self-heal sweep now only enqueues when `waiting < MAX_WAITING_RUNS`, so it keeps the pipeline busy without flooding it. Plus: the KI-tab verdict banner now colours by finding severity (red/amber/green) so a settled-but-not-shop-ready item stands out. 1214 pass; tsc clean. → [agentic]
1057. ✅ **Transcript viewer — "what the agent did", inline (KI-Runs surface, slice 1).** The only window into a run was a raw-JSON "Protokoll öffnen" link. New `TranscriptViewer` renders the stored transcript as collapsible per-stage sections (search→extraction→supervisor→…→wording) in the KI tab — each stage's response, with request/messages/tool-calls nested, German labels, last stage open. Loads on demand from the existing `TranscriptUrl` (no new backend); raw-link fallback for legacy transcripts. First slice of the planned KI-Runs surface, pulled forward from existing data. 1211 pass; tsc clean. → [ui]
1056. ✅ **Enrol-time triage — skip the full run for refs whose data is already good (validate-only).** The feeder enrols every run-less ref (462) for a full search→extraction→categorization run; many already have good data, wasting LLM calls and risking churn. New validate-only path assesses the *existing* content and hands it to the auto-approve gate with no LLM. `isValidateOnlyEligible(ref)` (has a spec contract + no block/warn finding) routes already-good refs to it at enrol; the rest get a full run. Triage only ROUTES — approval stays the result handler's separate gate. Rides `pendingValidateOnly`; `runItemFlow` branches after `buildSpecContext`. 1211 pass; tsc clean. → [agentic]
