# Changelog: QR Codes & Scanning

Covers: QR code generation, scanner workflows, scan audit logging, search-scan mode, return-to routing.

---

## 886. ✅ Scanner: visual scan feedback + explicit exit (and loop exit → inventory reconciliation)
   - **Why:** (1) The camera scanner (`QrScannerPage`) gave **no** feedback on the placement/return scan path — `triggerSuccessFeedback()` (beep + vibrate) was only wired into the `searchTarget` branch, and there was no visual cue anywhere. Added a `signalSuccess`/`signalMismatch` pair that combines the existing audio+haptic with a full-frame flash overlay (green ✓ / red ✗, `qr-flash` + `video-frame--success/error` border) and wired success into **all** resolve branches (placement return, callback-navigate, plain navigate) plus mismatch/error into the failure branches. A short `delay(280)` before navigating makes the flash perceptible before the view changes. (2) The scanner had **no exit** — the only way out was browser-back, and in the placement loop each scan bounced straight back to the camera, so there was never a moment to stop. Added a persistent toolbar with a **"✕ Schliessen"** button (`handleClose`).
   - **Why (approach):** For `intent === 'placement-scan'`, Schliessen doesn't just `navigate(-1)` (which would land on `PlacementScanView` and immediately auto-bounce back to the scanner). Instead it returns a `{ qrReturn: { intent: 'placement-scan', finish: true } }` signal; `PlacementScanView` detects `finish` and runs the exit reconciliation (`finishInventory`, storage #885) rather than looping. The finish handler is late-bound via a `finishInventoryRef` because the scan-return effect is declared above `finishInventory` (avoids a TDZ reference). All other intents fall back to `navigate(-1)`.
   - **Deferred:** The 280 ms success hold is a fixed constant, not configurable. No distinct sound per outcome beyond the existing success/mismatch tones. The scanner still auto-starts the camera on mount (no manual "start" gate) — the toolbar title + Schliessen were judged sufficient for the "clear entry/exit" ask.

## 882. ✅ Hardware barcode scanners no longer submit the focused form
   - **Why:** Keyboard-wedge scanners "type" the barcode into the focused input and emit a trailing Enter; that Enter fired native implicit form submission (and `onKeyDown` Enter actions) across ~15 screens, breaking operator flows. There was no hardware-scanner handling at all — every existing "scan" feature is the camera `BarcodeDetector`, unrelated. Fixed with a single document-level, **capture-phase** `keydown` listener mounted once in `App.tsx` that uses a pure keystroke-timing detector (`frontend/src/utils/scannerDetection.ts`, `createScanDetector`): a fast burst (gaps <30 ms, ≥3 printable chars) terminated by a fast Enter is treated as a scan, and only that Enter is `preventDefault`+`stopPropagation`'d. Capture phase runs before React handlers and native submit, so one listener neutralizes every form at once; the barcode characters still land in the input normally.
   - **Why (approach):** Chose timing-based detection over blanket "block all Enter-submit in single-line inputs" so human Enter-to-submit is preserved (wedge scanners are >10× faster than human typing, so the two are cleanly separable). Detection logic kept DOM-free in `utils/` for unit-testability; DOM wiring is a thin `useEffect` in `App.tsx`, consistent with existing components that attach their own `document` keydown listeners. Added a `frontend/src/utils/__tests__` glob to `jest.config.cjs` so co-located util tests are discovered (pure + jsdom integration tests, 10 cases).
   - **Deferred:** No opt-in "scan-to-act" mechanism (e.g. a data attribute to let a dedicated field still act on a scanned Enter) — every scan currently fills-but-does-not-submit, per the request. Threshold/min-length are constants in `scannerDetection.ts` (not env/config) — revisit only if a slower scanner model needs tuning.

## 765. ✅ Four v3.0 release bugs fixed: mobile QR scan button added to header
   - **Why (mobile scan):** No QR scan button existed in the Header for general navigation. Added `QrScanButton` (mobile-only) to the header nav; after scan the scanner navigates to `/items/{id}` or `/boxes/{id}` which `ItemRoute`/`BoxRoute` handle with `setEntity` + `mobileShowDetail=true`.
   - **Deferred:** Artikel_Nummer attachment routing still goes to instance endpoint (label-only, unchanged from step 760).

## 752. ✅ Pre-release cleanup: QR search-scan CSS + EventLog empty state
   - **Why:** `.search-target-hint` / `.search-mismatch` classes were applied in `QrScannerPage` but had no CSS rules (deferred in step 751); added amber color for mismatch and muted gray for the search target hint, matching the existing `.qr-scanner` status palette. `ItemEventsTab` and `BoxDetail` events render silently produced an empty area when the events array was empty; added "Keine Aktivitäten." empty-state text to make the blank-vs-no-data distinction visible.
   - **Deferred:** If the events array is empty due to a deeper data-fetch regression (rather than genuinely no events), that path still needs investigation — the empty state now makes it visible instead of invisible.

## 751. ✅ QR search-scan mode: continuous scan resolves on target match with audio+vibration feedback
   - **Why:** Operators needed a "find this item/box" flow — scan QR codes until the right one is found, with instant tactile+audio confirmation. Reused the existing `QrScannerPage` + `QrScanButton` infrastructure; added a `searchTarget` URL param and `'search'` intent. On mismatch the camera stays open and a 1.5 s cooldown prevents re-triggering the same code while it's still in frame. Web Audio API + `navigator.vibrate` are used for feedback; both degrade gracefully if unavailable. "Finden" button added to the item instance tab (hidden when out-of-stock) and to the box/shelf tab-actions.
   - **Why (approach):** All new logic is behind a `searchTarget` guard — zero change to existing scan flows. Module-level feedback helpers avoid repeated AudioContext allocations. The `skipDetectionRef` cooldown ref (not state) avoids re-renders during the scan loop.
   - **Deferred:** No CSS added for `.search-target-hint` / `.search-mismatch` — these class names are in place for styling follow-up. The "Finden" button inherits `mobile-only` from QrScanButton (desktop operators can read the ID visually). No shelf-specific label override (uses `BoxID` for shelves).
