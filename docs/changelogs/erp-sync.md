## 942. ✅ Shopware: quality as a variant axis + manual Shop-Sync button (admin)
**Why:** Two operator-driven follow-ups. (1) **Quality becomes a variant dimension.** `buildVariantGroups` now injects each instance's quality label (`describeQuality(items.Quality).label` — Ersatzteil/Upcycling/Ok/Gut/Neuwertig) as a **`Zustand`** option (unknown `'?'` skipped). So instances that differ only in condition split into separate Shopware variants, and quality-only variants work even when InstanceSpecs are empty. No storage change — quality stays authoritative in `items.Quality`, injected at snapshot time. (2) **Manual "Shop-Sync"**, mirroring the ERP "Kivi Sync" list action: `POST /api/admin/shopware/sync` (admin-gated via `requireAdminAuth`). Body `{ itemIds }` → `enqueueShopwareSyncForItems` (resolves the selected instances' refs) for the **list bulk-action**; no body → `enqueueShopwareSyncForShopRefs` (every `Shopartikel=1` ref) for the admin card's **backfill-all**. The dispatch gate then does the right thing per ref (approved → full sync, unapproved/de-flagged → deactivate), so it also cleans up pre-gate skeletons. Frontend: a **"Shop Sync 🛒"** button in `BulkItemActionBar` (next to "Kivi Sync 🥝") shown **only when the operator holds the admin token** (`sessionStorage.adminSecret` — i.e. logged into the admin page), sending it as `Authorization: Bearer`; plus an "Alle synchronisieren" (backfill) button on `ShopwareStatusCard`. No-op with a clear message when `SHOPWARE_SYNC_ENABLED` is off.
Verified: quality-axis grouping 4/4 (same specs + different quality → 2 variants; quality-only variants; unknown quality omitted); all changed modules esbuild-resolve; no tsc errors.
**Deferred (operator decisions):** contract-driven property curation and CO₂ badges are explicitly **not** pursued (all properties already come from the items; no benefit adding contracts). **Stock-back** (orders in Shopware → book out mediator stock) is the open design item — see the runbook's "Reverse sync" note; recommendation is the `checkout.order.placed` webhook (poll fallback), not yet built.

## 941. ✅ Shopware variants (P2c): ref → parent product, instance-spec combos → variant children
**Why:** Instances of one Artikel_Nummer differ by `InstanceSpecs` (RAM/storage per unit). The mediator's ref/instance relation maps onto Shopware's parent/variant model, and the schema already had `item_refs.ShopwareProductId` (parent) + `items.ShopwareVariantId` (per-instance) for exactly this. Shopware variants are built on the same property-group/option system as P2a, and require **unique option combinations** per child — so the model is: one variant per **distinct InstanceSpecs combination**, stock = summed instances sharing it (identical-spec units merge into one variant with stock N; unique specs ⇒ effectively one variant per instance).
- **Grouping** (`db.ts buildVariantGroups`): a ref's instances are grouped by a canonical InstanceSpecs signature (sorted `key=value`, array values joined) → `{ key, options, stock, instanceIds }`. Used only when **≥2 distinct combos AND every group carries options** (a spec-less instance can't be a valid variant); otherwise the existing single-product path (summed stock) stands. `getShopwareSyncSnapshot` now also loads the ref's instances and attaches `variants`.
- **Sync** (`adminClient.syncVariants`, called from `upsertProduct` when `variants.length ≥ 2`): resolve each combo's spec values to property options (reusing P2a `ensurePropertyGroup`/`ensurePropertyOption`), PATCH the parent's `configuratorSettings` with the axis options, then upsert one **child product** per combo — deterministic `productNumber = parent.suffix` (sha1 of the signature), `parentId` + `options` + summed stock, **inheriting price/tax/visibility from the parent**. On re-sync an existing child gets stock/active PATCHed (its options/identity are fixed); a combo that no longer exists is **retired** (child `active:false, stock:0`, not deleted). Returns instance→child-id assignments.
- **Persistence**: `syncClient` writes each instance's `ShopwareVariantId` via the injected `setItemShopwareVariantId` (wired in `server.ts`).
Verified via injected-fetch mock: grouping 4/4 (merge identical, sum stock, key-order-independent, array-join); variant flow 7/7 (2 children under parent with their options + summed stock, configurator gets both axis options, stale child deactivated+zeroed, assignments cover all instances); gate 11/11 + property 3/3 unchanged.
**Shopware mechanics to validate on a live instance** (can't verify against a real Shopware here): the `configuratorSettings` write and the child `options` write semantics — mirrors the P2a m2n uncertainty; if a live shop reveals a different behavior, adjust as with properties. **Deferred:** ragged specs (an instance missing an axis others have) fall back to single-product rather than a partial variant matrix; a single distinct combo isn't turned into a variant (stays single product; its InstanceSpecs aren't yet surfaced as parent properties); no per-variant price; child media/images (P3).

## 940. ✅ Shopware sync: shop-eligibility gate, published→active, full product data + visibility
**Why:** Live testing found three problems: (1) **unreviewed / non-shop items landed in Shopware** — sync ran for every item regardless of the shop flag or approval; (2) only a **name+stock skeleton** was written (specs/properties did sync, but description, price and the active/visibility state did not); (3) `Veröffentlicht_Status` (published) wasn't mapped to Shopware `active`. All three: the dispatch did too little and gated nothing.
- **Shop-eligibility gate.** `getShopwareSyncSnapshot` now computes `shopEligible = Shopartikel === 1 AND agentically approved`, reusing the ERP approval definition (`ReviewState` authoritative, else `Status`, ∈ {approved, auto_approved}; inlined as `isAgenticApproved` to avoid an actions→db cycle; approval read via scalar subselects so multiple `agentic_runs` can't corrupt the stock SUM). In `upsertProduct`, an **ineligible** item is never published: **deactivated** (`active:false`) if it already exists in Shopware, **skipped** otherwise. So an unreviewed or de-flagged item never goes (or stays) live.
- **published → active.** Snapshot `active = Veröffentlicht_Status === 'yes'` (via the shared `normalizePublishedValue`), written to the product's `active`.
- **Full data on create AND update.** A shared `buildProductFields` writes name (**Artikelbeschreibung** = the ERP article title), description (**Kurzbeschreibung** = notes, when it differs from the name), price (gross + net computed from the tax rate, in the sales-channel currency), **dimensions** (`Länge_mm`/`Breite_mm`/`Höhe_mm`→length/width/height, `Gewicht_kg`→weight, each sent only when set), `active` and stock — the **update** path previously PATCHed stock only. New `ShopwareUpsertResult.action` includes `deactivated`/`skipped` (productId nullable).
- **Storefront visibility on create.** A product needs `active` **and** a sales-channel visibility to appear; create now sets `visibilities:[{salesChannelId, visibility:30}]` for the configured channel (resolved via the merged `resolveSalesChannel` by `accessKey` → id+currencyId, one cached lookup for both currency and visibility). Without this, published products stayed invisible.
Verified via injected-fetch mock, 10/10 gate + 3/3 property: eligible update writes full data; eligible create writes full data + taxId + visibility; ineligible+exists deactivates (no tax/price work); ineligible+missing skips with zero writes; sync client persists id only on `created`, drains `skipped`/`deactivated`.
**Deferred / notes:** Items with **no agentic approval never sync** (matches the ERP gate) — a purely manual shop item would be blocked; make the approval requirement configurable (like `ERP_SYNC_REQUIRE_APPROVAL`) if that bites. **Pre-existing skeleton products** created before this fix only correct themselves (full data, or deactivation) on their **next enqueue** (a save/stock change); a bulk re-sync of shop refs would force it. Visibility is set on **create** only; products created before this fix won't gain visibility on update (re-create or a one-off backfill needed). Name/description field mapping is a heuristic — adjustable. Images are still P3.

## 939. ✅ Fix Shopware create-product 500 on currency resolution (runtime field in criteria)
**Why:** New-product creation broke in production with `FRAMEWORK__RUNTIME_FIELD_IN_CRITERIA: Field currency.isSystemDefault is a Runtime field and cannot be used in a criteria`. `resolveCurrencyId` filtered `POST /api/search/currency` on `isSystemDefault=true`, but that is a Shopware **runtime** field (computed on read) and is rejected in a search filter. Symptom timing was the tell — currency is only resolved on the **create** path, so the first ~half of items (which matched existing Shopware products → PATCH stock only) synced fine; the first item needing creation hit the bad query and, being a 500 (retryable), wedged all subsequent new-product syncs. Fix: resolve the currency from the **sales channel** instead — `POST /api/search/sales-channel` filtered on `accessKey` (a real, filterable field), reading its `currencyId`. This also yields the *correct* currency for the channel (e.g. CHF for a Swiss shop) rather than assuming EUR. Falls back to Shopware's seeded system-default currency id (`b7d2554b…`, EUR) **without caching** so a transient lookup failure can't pin the wrong currency for the process lifetime; a real answer is cached. The previously-failed jobs sit `queued` with backoff and retry to success after redeploy — no manual queue surgery. Verified 17/17 (create currency from sales channel; never queries the runtime field; fallback-to-constant on lookup failure).
**Deferred:** nothing beyond the existing P2 backlog.

## 938. ✅ Shopware property sync (P2a): Langtext/Spezifikationen → filterable properties
**Why:** Stock sync (P1) made items *land* in Shopware but they were undifferentiated — no specs, not filterable. Operator insight sharpened the plan: use Shopware **properties** (property group + options), not custom fields, because properties are the storefront's native, auto-built filter system (custom fields are not filterable without theme work). Every structured Langtext entry (`item_refs.Langtext` parses to `Record<string, string|string[]>` — canonical German spec keys like `Prozessor`/`Display`/`Anschlüsse`) maps 1:1 to a property group → option(s).
- **adminClient** (`ShopwareAdminClient`): `upsertProductStock` → renamed `upsertProduct`, now also reconciles properties after stock. New `syncProductProperties(productId, payload)`: for each `group → value(s)`, `ensurePropertyGroup` (search `property-group` by name; create `filterable:true, displayType:text` if missing) + `ensurePropertyOption` (search `property-group-option` by groupId+name; create if missing), both **cached** across jobs. Then sets the product's associations to **exactly** the desired options — robust to either Shopware association-write semantic: PATCH the full desired list (a "replace" build lands exactly this; an "upsert" build just adds), then explicitly `DELETE` stale option links (404-tolerant). Array Langtext values → multiple options under one group.
- **DB**: `getShopwareSyncSnapshot` now selects `Langtext`, parses it (`parseLangtext`), and passes the **object** form as `properties` (freeform prose → null, not filterable). `ShopwareSyncSnapshot.properties` added.
- **syncClient/snapshot**: `ShopwareProductSnapshot.properties` threaded through; property errors ride the same retry classification (4xx terminal, 5xx/network retryable) — stock is set first, so a property hiccup never loses the stock update, and a retry re-runs idempotently.
Verified via injected-fetch mock: P1 suite still 15/15 after the rename; new property cases (create-missing-group+option+link+remove-stale; array→2 options under a reused existing group, group not re-created, both linked). All modules esbuild-resolve; no `tsc` errors in changed files (full `tsc` unavailable locally — no `@types/node`).
**Why properties over custom fields:** properties auto-generate storefront listing filters and are the Shopware-idiomatic home for discrete specs; custom fields would need bespoke theme work to filter. **Deferred:** contract-driven curation (today **all** Langtext keys become properties; using `contracts/specs/*.json` to pick which are filterable / rename display labels / units is a follow-up); no property-group translations/position/units; the m2n dual-write is defensive — confirm the exact association semantic against a live Shopware and simplify if desired. Digit-only numeric sorting (`sortingType` stays alphanumeric).

## 937. ✅ Shopware stock sync live (P1): Admin-API write client + worker wired
**Why:** With the read path green and P0 cleanup done, the plan's foundation is the write path. Operator decisions: **direct-to-Shopware**, **create-if-missing**, **absolute stock**. That trio collapses every job type into one idempotent operation — reload the item, upsert its product by `productNumber = Artikel_Nummer`, set stock = current summed quantity — so a missed or duplicated job self-heals.
- **Admin-API write client** (`backend/shopware/adminClient.ts`, new). Distinct from the store-api read client: admin writes authenticate with a **bearer token** (client-credentials grant preferred since admin tokens expire; static `SHOPWARE_ACCESS_TOKEN` accepted), not the sales-channel key. Ops: `findProductIdByNumber` (`POST /api/search/product`), `updateProductStock` (`PATCH /api/product/{id}` writing `stock`, not the computed `availableStock`), `createProduct` (client-generated 32-hex id; name/number/stock/taxId/price with net computed from the tax rate), and the composed `upsertProductStock`. Tax/currency resolved from Shopware at runtime (highest rate = standard; system-default currency; EUR fallback) unless pinned via `SHOPWARE_DEFAULT_TAX_ID` / `SHOPWARE_DEFAULT_CURRENCY_ID` (new optional config).
- **Dispatch client** (`backend/shopware/syncClient.ts`, new) replaces the old `queueClient` stub. Maps a job → DB snapshot → `upsertProductStock`; persists the new `ShopwareProductId` back on create; classifies failures (4xx except 408/429 = terminal; network/408/429/5xx = retryable); a deleted reference (null snapshot) drains as success. DB access is injected so it stays unit-testable.
- **DB** (`backend/db.ts`): `getShopwareSyncSnapshot(artikelNummer)` (summed `Auf_Lager` across instances + name/price/ShopwareProductId), `getShopwareSyncSnapshotForPayload` (resolves Artikel_Nummer from `itemUUID` for move/stock jobs whose thin payload lacks it), `setShopwareProductId`.
- **Worker wired** (`backend/server.ts`): the old "not implemented" reminder is replaced by a real 10s reentrancy-guarded `processShopwareQueue` loop, started only when `SHOPWARE_SYNC_ENABLED` and the config is ready. Also fixed the worker's DB status-transition calls (`markSucceeded`/`reschedule`/`markFailed`) to be **awaited** (they were fire-and-forget from the SQLite era, now async Postgres).
Verified via injected-fetch mock, 15/15 assertions (existing→PATCH stock, missing→create with highest-tax pick + computed net + currency, token fetched-once/cached; sync skip-on-null, persist-id-on-create, 400-terminal / 500+network-retryable). `tsc` unavailable locally (no `@types/node`) — also checked by grep sweep, esbuild resolution of all modules incl. `server.ts`, and a `strictFunctionTypes` fix on the injected snapshot loader.
**Deferred:** Queue **retention/trim** (succeeded rows accumulate). Created products get **no sales-channel visibility** (operators publish via the existing shop flow). **No max-retry ceiling** on transient failures (retries with backoff until Shopware recovers). Richer product data — custom fields (Langtext), media (images/docs), quality/CO₂ badges, accessory cross-selling — is P2–P4. Full product-normaliser dedup between the store and admin clients still pending. Poll interval hardcoded at 10s (the `SHOPWARE_QUEUE_POLL_INTERVAL_MS` env stays retired).

## 931. ✅ Admin "Backup" made a complete, restorable, env-independent snapshot
**Why:** The admin "Backup" button was underdefined and could not actually restore current state. It routed to `GET /api/export/items?mode=backup`, which has two disqualifying properties for a backup: (1) it emits **only** `items.csv` + `boxes.csv` — agentic runs and the event log are absent — and (2) its Langtext serialization went through `resolveLangtextExportFormat`, which honored `LANGTEXT_EXPORT_FORMAT` **first**. When that env var was set to `html` (its whole purpose is the ERP boundary, changelog #830), even a *backup* serialized Langtext as an HTML `<table>` and wrapped Kurzbeschreibung in `<p>…</p>` — HTML in CSV cells that the importer cannot parse back, so the "backup" was not restorable. The operator's requirement: a backup must be a full CSV archive (restorable via the existing `/api/import` ZIP path, which already ingests `items/boxes/agentic_runs/events`), with Langtext as JSON and every other cell plain text, regardless of env config.

Changes:
- **Backend `export-items.ts`:** `resolveLangtextExportFormat` now returns `'json'` for every non-ERP mode **unconditionally** — the `LANGTEXT_EXPORT_FORMAT` override is confined to `erp` mode (default `html`). This makes backup cells deterministic (JSON Langtext; the HTML Kurzbeschreibung path is gated on `format==='html'` and therefore never fires for a backup).
- **Frontend `ExportCard.tsx`:** the "Backup" button routes to `/api/export/data?format=zip&mode=backup&entities=items,boxes,agentic,events` — the only multi-entity export — producing one ZIP with all four CSVs the importer ingests. The ERP/partner modes (`erp`, `manual_import`, `automatic_import`) stay on `/api/export/items`.
- **Backend `export-data.ts` (latent bugs fixed while wiring backup through it):** the boxes, agentic, and events queries used **unquoted CamelCase identifiers** (`SELECT Id, Artikel_Nummer, …`) against columns defined as case-sensitive quoted CamelCase, so Postgres folded them to lowercase and every one of these three queries threw at runtime — this endpoint had never actually produced boxes/agentic/events output. Quoted all identifiers. Added `"LastSearchLinksJson"` to the agentic SELECT/columns (the importer's `ingestAgenticRunsCsv` reads it, so a backup must carry it or stored search evidence is lost on restore). Made backup **uncapped** — the 500-row (`MAX 5000`) `LIMIT` on agentic/events would silently truncate a real backup; it now applies only to non-backup callers.

**Deferred:** No JSON restore importer — restore stays CSV/ZIP-based per the operator's decision that a backup "should be CSV", so the backup is a ZIP-of-CSVs rather than a single JSON file. The `manual_import`/`automatic_import` buttons remain distinct UI entries even though internally `manual_import`≡`backup` and `automatic_import`≡`erp` (only two real regimes); collapsing/relabeling that UI is a follow-up, not done here. `/api/export/data` remains unauthenticated (same as `/api/export/items`); gate under the Authentik/role model (todo 33c) if backups should be access-controlled.

## 879. ✅ Gate ERP export/sync to approved items only (configurable)
