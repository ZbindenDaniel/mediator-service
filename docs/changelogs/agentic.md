## 915. ✅ AI-runs phase 1a: raise the model HTTP timeout wall + make queue-level terminal transitions traceable
**Why:** First implementation slice from the AI-runs design doc (#914), covering the two decision-free, highest-urgency threads. **(1) Ollama `UND_ERR_HEADERS_TIMEOUT` (Thread 5).** `ChatOllama` runs on Node's global `fetch` (undici) with no raised `headersTimeout`, so a slow first token from a cold/large local model (`invoker.ts` `loadModel`) was misclassified as a transport failure; `withLlmRetry` then re-sent the whole prompt into the *same* wall and the run terminated `failed`. Root fix: `ensureModelHttpTimeouts` (`utils/http-dispatcher.ts`) installs a `setGlobalDispatcher(new Agent({ headersTimeout, bodyTimeout }))` once, before any model client is built (awaited at the top of `loadModel`, idempotent + best-effort). Defaults 600000 ms (10 min, matching `OLLAMA_KEEP_ALIVE`), configurable via `MODEL_HTTP_HEADERS_TIMEOUT_MS` / `MODEL_HTTP_BODY_TIMEOUT_MS` (`config.ts` `modelHttpConfig`); `0` disables. `withLlmRetry` stays as the fallback for genuine transport drops (its comment was retargeted). Added `undici@^6` as a direct dep (Node 22 already bundles undici 6; the package is needed for `Agent`/`setGlobalDispatcher`). **(2) Untraceable waiting→failed (Thread 4B).** Three queue paths terminated runs as `failed` with only a `logger.warn` and **no item event** — `stale-run-auto-cancelled`, `over-cap-cancelled` (both `dispatchQueuedAgenticRuns`), and `missing-search-query` — so the transition showed up nowhere in the item's history. New `recordQueueTerminalTransition` helper emits a structured `from → to / reason` log line **and** an `AgenticRunFailed` item event (via the existing `logEvent` dep) at all three sites, with a `category` tag (`infra-cancelled` for capacity/zombie reclaim vs `invalid-state` for the empty query) so an infrastructure cancellation is distinguishable from a genuine failure. Env docs added to `.env.example` + `ENVIRONMENT.md`.
**Why (approach):** The undici dispatcher is deliberately **global** rather than per-request: Node's built-in fetch (used by the `ollama` browser build) reads the global dispatcher, whereas a scoped dispatcher would require the ollama client to forward a custom `fetch` — not guaranteed by its published surface. The side effect is acceptable because only the *ceilings* rise (fast APIs answer well within them; Tavily also self-bounds with its own AbortSignal). The terminal **status** was intentionally left as `failed` (not a new state) in this slice — separating infra-cancel into its own non-terminal/re-queue class is Thread 4A, which carries an open design question (re-queue vs terminal) deferred to a later slice. Reused the existing `AgenticRunFailed` event name (not a new type the frontend can't render); the distinction rides in `Meta.category`.
**Deferred:** Thread 4A (separate infra-cancel state / re-queue-instead-of-fail) and Thread 4C (repair an empty `SearchQuery` instead of failing — needs Thread 1's structured identity) not done here. Thread 2A (surface these sources/queries in the UI) is the next slice. Supersedes the 0z2 deferral note "Ollama header timeout mitigated via keepAlive+retry rather than a custom dispatcher" — a dispatcher timeout is now set. Per-run state-transition audit table (vs the item event) not added; `MODEL_HTTP_*` timeouts apply globally to all fetch, not just the model host.

## 914. 📝 Design doc: AI runs optimization (`docs/PLANNING_ai_runs_optimization.md`)
**Why:** Five agentic-run pain points were converging and being triaged piecemeal; scoping them together surfaced a single root frame — **the run is an opaque, un-steerable object** — that a per-thread fix would keep missing. The doc analyses each thread against the current code (with `file:line` references) and proposes options + a recommendation per thread, plus a shared observability/evidence backbone and a build sequence, as the basis for a brainstorm before any implementation. Threads: (1) **grounding** — the search anchor *is* the raw `Artikelbeschreibung` (`agentic-trigger.ts:156`, `index.ts:1401`, `item-flow-search.ts:937`) with no structured-identity anchor and no post-search relevance gate, so a bad description extracts wrong-item data (the "PC → Pokémon cards" case); (2) **visibility** — `LastSearchLinksJson` is persisted (`invoker.ts:931`) but never read by `frontend/src`, so operators can't see stored evidence or query counts; (3) **rework closure** — `canRework` is gated `!needsReview` (`ItemKiTab.tsx:72`) so it's unreachable during review, and a failed rework demotes an already-good item to `failed` (documented-deferred in item-flow.md/todo #50); (4) **state machine** — there is no `waiting` status (it normalizes to `queued`, `agentic-statuses.ts:42`) and three queue paths silently terminate runs as `failed` with only a `logger.warn` and no `logEvent` (`missing-search-query` `index.ts:1220`, `stale-run-auto-cancelled` `index.ts:1100`, `over-cap-cancelled` `index.ts:1138`), conflating infra-cancel with pipeline-fail; (5) **Ollama timeout** — `ChatOllama` uses global undici `fetch` with no raised `headersTimeout` (`invoker.ts:490`), so a slow first token is misclassified as transient and `withLlmRetry` (`invoker.ts:67`) re-sends the whole prompt into the same wall (the recurring `UND_ERR_HEADERS_TIMEOUT`).
**Deferred:** No behavior/code change — this is analysis + proposal only. All decisions (grounding-anchor precedence, relevance-gate outcome, whether over-cap should re-queue instead of fail, transition-trail storage, rework pre-state memory, Ollama dispatcher scope) are left open for the brainstorm and captured in the doc's "Open questions" section. Consolidates related todo items #9, #10, #11, #21, #22, #23, #24, #25, #49, #50, 0-1, 0z2.

## 913. ✅ Harden the agentic auto-dispatcher (demote keep-busy, kill switch, terminal failures, transient retries)
**Why:** Incident — the auto-dispatcher burned ~1000 search queries in minutes and revived runs the operator had stopped ("no matter how many I stop there's always a few waiting"). Root causes were compounded in the keep-busy path added in #908/#909: (a) `claimIdleFillAgenticRuns` reset `RetryCount = 0` on every claim, defeating the `MAX_AUTO_RETRIES` ceiling so a permanently-failing item retried forever; (b) it claimed `failed`/`cancelled` runs, so an operator `cancelled` (and an auto-`failed`) run was auto-resurrected — a human stop was not durable; (c) the #909 "searches at most once" invariant was false for the failing items, because `collectSearchContexts` threw on the *first* failed plan **before** `persistSearchLinks` ran, so a failed search never persisted links and every retry re-billed the provider. Fast-failing Tavily errors (`200 Error: undefined`) + 3 slots + a 5s tick + no ceiling produced the burst.

Per the operator's direction the auto-dispatcher was **demoted to a `notStarted`-only feeder**, and failures made terminal. Changes:
- **DB (`db.ts`):** replaced `claimIdleFillAgenticRuns` with **`claimNotStartedAgenticRuns`** — promotes only `notStarted` → `queued` (never `failed`/`cancelled`), `FOR UPDATE SKIP LOCKED`, and does **not** touch `RetryCount`/`LastAttemptAt` (promotion to the waiting queue is not an attempt).
- **Dispatcher (`index.ts`):** the feeder now tops up the **waiting** queue up to `MAX_WAITING_RUNS` (= `MAX_CONCURRENT_RUNNING_RUNS`, so ≤ N running + N waiting) and no longer promotes straight to running or invokes the model — the normal `queued → running` claim drains it on a later tick. The feeder still runs when all running slots are busy (so the waiting buffer stays full). `autoCancelAfterFailure` and the stale-run sweep now land in **terminal `FAILED`** (no auto-requeue/backoff); the `MAX_AUTO_RETRIES`/`RETRY_BACKOFF_MINUTES` constants are gone. Added an admin kill switch `agentic_auto_dispatch_enabled` (default ON when unset) read via `getSystemSetting`; when off, the feeder (and the idle contract-audit sweep) are skipped while explicit user-triggered runs still dispatch.
- **Kill switch UI:** `admin-agentic-dispatch.ts` (GET/POST `/api/admin/agentic-dispatch`, admin-auth) + `AgenticDispatchCard.tsx` on the Admin page, mirroring the Nightly-ERP-Sync toggle.
- **In-process resilience** (the safety net that makes "failed = terminal" acceptable): Tavily client (`tavily-client.ts`) retries transient failures (timeouts, 5xx, the malformed-2xx `200 Error` anomaly) with backoff and passes a shorter per-request `timeout` (20s) so a hung request fails fast; 4xx/429 are not retried (429 still surfaces as `RateLimitError`). `collectSearchContexts` is now **per-plan tolerant** — one plan's transient failure no longer aborts the run; it fails only if *every* plan failed, so partial results survive and get persisted for a search-free retry. The Ollama client (`invoker.ts`) sets `keepAlive` to keep the model resident and wraps `invoke` in a transient retry (targets undici `UND_ERR_HEADERS_TIMEOUT` on cold model load).
**Why (approach):** The operator explicitly scoped the auto-dispatcher down to "feed unstarted runs, full stop — all other states have a reason to be idle." Making `failed`/`cancelled` ineligible for auto-claim (rather than adding more cooldown/ceiling logic on top of #909) is what makes an operator stop durable and stops the resurrection loop at the source. Terminal failures + in-process retries move recovery *inside* a run (bounded, no re-billing storm) instead of resurrecting whole runs through the dispatcher. The kill switch reuses the existing `system_settings` + admin-card pattern, so it needed no new storage or auth. Capping waiting with the same `MAX_CONCURRENT_RUNNING_RUNS` parameter keeps configuration to one knob.
**Deferred:** The kill switch scopes to the auto-feeder only (explicit triggers still run) — no global emergency-stop of the whole dispatch loop. Failed runs now require a manual re-trigger (no automatic recovery); this is intentional. `MAX_WAITING_RUNS` is hardwired to the running cap rather than separately configurable. The Ollama undici header timeout is mitigated via `keepAlive` + retry rather than a custom dispatcher `headersTimeout`, since LangChain's `ChatOllama` does not cleanly expose one. Tavily's `timeout` option is passed best-effort (ignored by SDK versions that don't support it; the retry still bounds latency).

## 910. ✅ Category-level `guidance[]` prompt snippets on spec contracts
**Why:** Operators need a place to give the LLM standing, per-subcategory instructions for things it repeatedly gets wrong (e.g. "Laptops: do not mention the OS in the prose", "3.5\" HDDs usually measure XYZ mm"). The prompt-injection machinery already existed — the `{{EXTRACTION_REVIEW}}`/`{{SUPERVISOR_REVIEW}}` placeholders fed by `appendPlaceholderFragment` + `sanitizePromptFragment` — but nothing let a human author free-text snippets keyed by category. Option A (a field on the existing spec contract) was chosen over a new DB table + admin UI (Option B): it reuses the loaded-and-cached `getSpecContract` path, versions the snippets in git next to the field definitions, and needs no migration. Added optional top-level `guidance?: string[]` to the `SpecContract` type (`models/spec-contract.ts`); `item-flow.ts` resolves it alongside the existing `specContractVersion`/`buildSpecContext` (same `subcategoryCode`, cached contract) and threads it into `runExtractionAttempts` as a new `categoryGuidance` option; `item-flow-extraction.ts` appends each non-empty entry to the **extraction** (factual hints) and **supervisor** (enforcement) review placeholders via `appendPlaceholderFragment` — reusing its sanitizer (code-fence/role-prefix stripping, 400-char cap) — and logs an injection summary. Injected to extraction + supervisor but **not** the categorizer (which decides category, not content). Seeded `contracts/specs/201.json` (laptops) with the OS example as a live demonstration; documented the field in `contracts/specs/README.md`. Test: new case in `item-flow-trigger-fragments.test.ts` asserting the snippet reaches both the extraction and supervisor messages.
**Why not a version bump:** guidance is advisory and changes no stored data, so adding/editing it does **not** require bumping the contract `version` (unlike `fields`) — deliberately, to avoid the idle contract-audit sweeper (#894) re-enriching every settled item in the subcategory on every wording tweak. Bump `version` only when you *want* that re-enrichment.
**Deferred:** No admin UI for editing snippets at runtime (Option B) — snippets are git-authored for now. "Do not mention X"-style suppression is injected as prompt guidance only, not enforced as a hard supervisor gate, so a determined model can still leak it; promote to a validated gate later if telemetry shows leakage. No frontend rendering of `guidance` (optional field, backend-only concern). Only `201.json` seeded; other subcategories left empty pending operator input.
## 909. ✅ Auto-retry failed/cancelled runs without re-searching (invoker-level search reuse)
**Why:** Follow-up to #908. Most runs settle as `failed` or `cancelled`, and the operator wants those retried automatically — but the reason not to before was the search-token burn. Fix gates the retry on *whether we already have search results* rather than on status: reuse the stored search and only hit the provider when we genuinely lack results. Three coordinated changes: (1) **`claimIdleFillAgenticRuns` broadened** to also claim settled `failed`/`cancelled` runs (with a `SearchQuery`), gated by a cooldown (`LastAttemptAt` older than `retryCooldownMinutes`, default 60) and `NextRetryAt`, ordered fresh-`notStarted`-first; it resets `RetryCount` so a retry gets a clean cycle. The cooldown keeps a permanently-broken item to a periodic retry instead of every 5s tick. (2) **Search reuse moved into the invoker as the single decision point** (`invoker.ts`): it now reuses stored `LastSearchLinksJson` whenever present and downgrades to a live search only when none exist — regardless of the transient `skipSearch` flag — *except* when a reviewer flagged missing spec fields (`missing_spec`), which still forces a targeted live search. Because every path (first run, in-cycle retry after a failure, keep-busy retry of a settled run, plain restart) funnels through the invoker, an item now hits the search provider **at most once until it is reset**. (3) **Search results are persisted the moment they're retrieved** — new `persistAgenticSearchLinks(artikelNummer, linksJson)` (`db.ts`) called from `runItemFlow` right after `collectSearchContexts` via a new optional `persistSearchLinks` flow dep wired in `invoker.ts`. Previously `LastSearchLinksJson` was only written on the terminal result dispatch, which a **failed** run never reaches — so a run that searched, got results, then failed at extraction would re-search on every retry. Now the results survive the failure and the retry is search-free. Regression test in `dispatch-queue-concurrency.test.ts` covers the atomic idle-fill claim (reserving 1 slot) invoking the model exactly once.
**Why (approach):** Put the search-vs-reuse choice in the invoker (one data-driven decision on stored results + review directives) rather than threading a `skipSearch` flag through every dispatch path — the flag was per-dispatch and lost across the fail→requeue cycle, so in-cycle retries re-searched. The `missing_spec` carve-out preserves the reviewer-directed "go find field X" live search. Reused the existing `LastSearchLinksJson` column and the invoker's stored-source reuse path (no new schema for the reuse itself; one tiny additive write helper).
**Deferred:** `retryCooldownMinutes` is a code default (60), not yet env/config-exposed; there is no hard cap on total auto-retries of a permanently-broken item — it retries periodically forever (search-free, and cheap when the model is local), so a stuck item is not silently abandoned. Auto-retrying user-`cancelled` runs (vs. only `failed`) is intentional per request but means a user stop can be revived after the cooldown; splitting that behind a flag is a follow-up if it proves surprising. Durable `skipSearch`/rework transport (todo #49) is still in-memory and unchanged.

## 908. ✅ Fix agentic search-token burn: atomically claim idle-fill ("keep-busy") runs
**Why:** Report — "the automatic dispatcher starts over and over again and we burn all our search tokens with the same search queries." Root cause is the idle-fill/keep-busy branch of `dispatchQueuedAgenticRuns` (runs every 5 s). Bulk imports deliberately create runs as `notStarted` **with a `SearchQuery`** so they don't flood the queue (`import-item.ts`: *"keep-busy picks them up when a slot is free"*). The queued path claims those atomically — `claimQueuedAgenticRuns` flips `queued → running` in a single `FOR UPDATE SKIP LOCKED` statement so a run is dispatched exactly once — but idle-fill used a **plain, non-atomic `SELECT`** (`fetchIdleFillAgenticRuns`) that never transitioned the run out of the `notStarted`/selectable state. So the same `notStarted`+`SearchQuery` rows were re-selected and re-dispatched on every tick, re-billing the identical Tavily search queries. The mismatch compounded with `scheduleAgenticModelInvocation`'s promotion guard (`Status === 'running'`, written to match the atomically-claimed queued path): a `notStarted` idle-fill run could never satisfy it, so it never left `notStarted` and the busy-loop was permanent. Fix: renamed `fetchIdleFillAgenticRuns` → **`claimIdleFillAgenticRuns`** and rewrote it to mirror `claimQueuedAgenticRuns` — a `WITH … FOR UPDATE SKIP LOCKED` CTE that flips eligible `notStarted` rows to `running` (stamping `LastAttemptAt`, clearing `NextRetryAt`/`LastError`) and `RETURNING agentic_runs.*`. Each keep-busy run is now claimed exactly once (no re-selection ⇒ no repeat search), and because it is already `running` the promotion re-check passes, so keep-busy actually executes. Concurrency math is unchanged: idle-fill still claims at most `remainingSlots = MAX − running − scheduled − 1` (the reserved slot keeps an explicit trigger able to start immediately), so a cycle never exceeds `MAX_CONCURRENT_RUNNING_RUNS`. Retry/terminal semantics are unchanged: a failed idle-fill run requeues to `queued` with its `RetryCount` (bounded to `MAX_AUTO_RETRIES`), and a stuck `running` run is still recovered by the stale-run sweep. New regression test in `dispatch-queue-concurrency.test.ts` asserts the claim limit (reserving 1 slot) and that a claimed run invokes the model exactly once.
**Why (approach):** Reused the existing, proven `claimQueuedAgenticRuns` atomic-claim pattern rather than inventing a new dedup mechanism or relaxing the promotion guard — a plain SELECT + a `running`-only guard is exactly the inconsistency that caused the burn, and the single-claim invariant is what prevents re-billing. Claiming straight to `running` (vs. to `queued`) keeps dispatch immediate and matches the guard's documented expectation that a run reaching `scheduleAgenticModelInvocation` is already claimed.
**Deferred:** `notStarted` runs are still resumed only by the live dispatcher, not by `resumeStaleAgenticRuns` on startup (which handles only `queued`/`running`) — unchanged. Entry 876 only cleared `SearchQuery` on the delete path to stop that one re-promotion trigger; this addresses the general mechanism, so the delete-time clear is now belt-and-suspenders rather than the sole guard.

## 906. ✅ Fix `invalid input syntax for type integer: "201.0"` crash in reviewed-example selection (float-formatted subcategory strings)
**Why:** A production run logged `22P02 invalid input syntax for type integer: "201.0"` with `msg: 'failed to select reviewed example block for prompt'`. Root cause: the category columns (`Unterkategorien_A` etc.) are `TEXT` by design (they round-trip through ERP/CSV import), and some legacy rows hold float-formatted strings like `"201.0"`. PostgreSQL's **integer** input parser rejects a decimal point (`pg_strtoint32_safe`), so a direct `CAST("Unterkategorien_A" AS INTEGER)` throws — whereas `::NUMERIC` tolerates it. Two read sites still used the naive direct cast: `queryReviewedExamplesBySubcategory` (`invoker.ts`, the one that fired) and `listContractAuditCandidates`' `SubCategory` projection (`db.ts`). Both now use the codebase's established `ROUND(NULLIF(...,'')::NUMERIC)::INTEGER` pattern (already used at ~6 other sites), making the read robust regardless of stored format. The invoker failure was non-fatal (try/catch → falls back to `STATIC_EXAMPLE_ITEM_BLOCK`), but it silently degraded the prompt to a generic example instead of a subcategory-matched reviewed one. **Data remediation:** new one-time script `scripts/normalize-category-values.ts`/`.js` canonicalizes the four category TEXT columns in place (`"201.0"` → `"201"`), touching only numeric-but-non-canonical values and leaving NULL/empty/non-numeric untouched (idempotent). The write paths were verified already-safe: `prepareRefRow` runs `asNullableInteger`, and the two raw inserts (`catalog-spare-part`, `remove-from-device`) coerce to `number | null` — so no new write-time guard was needed; the bad data is purely legacy.
**Deferred:** Column type stays `TEXT` (deliberate, for ERP/CSV roundtrip) — not migrated to `INTEGER`. todo #0v (removing the duplicate `RAM`/`Speicher`/`Akku` fields from `contracts/specs/201.json`) was **not** bundled in: those are `required: true` and feed both the extraction prompt and the contract-audit sweeper via `SpecContractVersion`, so removing them is a behavior change needing a version bump + re-audit, not pure hygiene.

## 894. ✅ Idle contract-audit sweeper (deterministic auto-rework, Phase 2a) + SpecContractVersion stamping (#46)
**Why:** As agentic work becomes more automatic, re-apply the current spec contract to items enriched against an older version — without forking the executor (reuses the #893 rework pipeline). Two parts. (1) **Stamping (#46):** new additive `SpecContractVersion INTEGER` column on `agentic_runs` (`db.ts`, `ADD COLUMN IF NOT EXISTS`, mirroring `Confidence`); the flow computes `getSpecContract(sub).version` and threads it through the callback payload (`AgenticResultPayload.specContractVersion`) so `result-handler` stamps it on the run upsert (null on paths that don't carry it → COALESCE keeps the prior value). (2) **Sweeper:** `sweepContractRework` runs inside `dispatchQueuedAgenticRuns` **only when otherwise idle** (after idle-fill, slots still free) and **only when `AUTO_REWORK` is enabled** (new config flag, default off). It loads the oldest settled items (`listContractAuditCandidates`, `approved`/`auto_approved`, oldest by `LastModified`), and for each stale one (stored `SpecContractVersion < current`) applies a pure decision (`decideContractAuditAction`, exported + unit-tested): **rework** (missing required field ⇒ enqueue a targeted rework via the #893 `pendingRework` path, one per idle tick), **restamp** (already complete ⇒ cheap `stampAgenticRunContractVersion`, no rerun), or **skip**. Loop-safe: a reworked/re-stamped item gets the current version, so it isn't re-selected until the contract bumps again — no `LastAuditedAt` needed for this deterministic cut. No LLM in the decision. Tests: `contract-audit-decision.test.ts` (skip/rework/restamp).
**Why (design):** deliberately the "small and safe" first cut — deterministic contract re-application only, one added column, sweeper gated off by default, one enqueue per idle tick, slot reserved for real work.
**Deferred (Phase 2b):** the LLM **standards auditor** (language/style/wording) + its runtime-editable `contracts/guidelines/standards.json` (read fresh, no redeploy) + the `LastAuditedAt` cursor for periodic re-checks + per-window budget cap. Also deferred (separate behavior): on a rework **failure**, discard the changes and keep the prior `approved` state (today a failed rework lands in `failed` like any run). Reworked items otherwise follow the normal review/auto_approve path (no special-casing).

## 893. ✅ Targeted "KI Überarbeitung" rework via the main pipeline (partial field updates)
**Why:** Operators need to re-run enrichment on *specific* fields of an already-good item (e.g. two specs in the wrong language) without re-doing the whole item. Decision: route rework through the existing pipeline — no second executor — and solve *partial updates* so a rework of 2 fields can't silently alter the other 10. New inputs `reworkSpecFields`/`reworkInstructions` thread through the restart action → `restartAgenticRun` (transient `pendingRework` map, mirroring `pendingSkipSearch`) → dispatcher → invoker → `runItemFlow`. **Preservation is deterministic, not prompt-based:** at final assembly `applyReworkPartialUpdate` (`item-flow.ts`) starts from the ORIGINAL item and overlays the model's output ONLY for the selected keys (a key may be a top-level field like `Artikelbeschreibung` or a `Langtext` spec sub-key) — the model literally cannot change unselected fields, so no `__locked` list threaded through the stages and no change to `result-handler` (the payload's `Langtext` stays complete). The one guarded branch: **categorizer + pricing are skipped in rework mode** (a text fix must not re-categorize/re-price, and the categorizer is the most failure-prone stage). An imperative rework directive rides in front of any reviewer notes through the existing `{{EXTRACTION_REVIEW}}` path (no new placeholder). Frontend: a "KI Überarbeitung" button in `ItemKiTab` opens the existing `AgenticSpecFieldReviewModal` (checkbox fields + free-text) — kept local to the tab so it doesn't perturb ItemDetail's review-modal state — and posts a rework restart (`buildAgenticRestartRequestPayload` extended, `skipSearch:true`). Selectable fields = the two description texts + every Langtext spec key. Tests: `rework-partial-update.test.ts` (4 cases proving only-selected-change / preserve-the-rest).
**Deferred:** Durable transport for the rework params (a column vs. the transient `pendingRework` map) rides with the skipSearch-persistence follow-up (todo #49) — lost on restart-before-dispatch, which safely falls back to a normal re-run. Row-level click-select and right-click on spec rows are not wired yet (the modal's own field checkboxes cover selection); instance-level `InstanceSpecs` rework and a bulk cross-item rework are out of scope. The **automatic idle-time auditor/sweeper** (Phase 2 of the plan — re-apply current contract + standards audit when idle) is a separate follow-up (todo #50).

## 892. ✅ Auto-approve clearly-good runs to a new `auto_approved` state (flag-gated, ERP-eligible)
**Why:** Every enriched item required manual review, even when the extraction was unambiguously good. Now, when `AUTO_APPROVE` is enabled, a run whose extraction is "clearly good" is finalized as a new `auto_approved` status instead of being forced into `review`. "Clearly good" is computed in `runItemFlow` where all signals are in scope: supervisor PASS (`extractionResult.success`) + no missing-required spec fields (`specCtx.missingRequired`) + no ambiguous fields (`specCtx.ambiguousFields`) + extraction confidence ≥ `AUTO_APPROVE_MIN_CONFIDENCE` (default 0.8). The boolean rides the callback payload (`AgenticResultPayload.autoApprovable`); the actual gate lives in `result-handler.ts` where the pre-existing `supervisorAttemptedApproval` block previously always downgraded machine approvals to `review` — it now branches to `auto_approved` when the flag is on and the payload qualifies. `auto_approved` is a distinct status (new in `models/agentic-statuses.ts`, added to normalization + `RESTARTABLE`) so operators can sort/filter and choose what to sync; it is **ERP-eligible** (`resolveAgenticApproval` in `export-items.ts` now treats `auto_approved` like `approved`), and `Abschliessen` still promotes it to full `approved`. UI: distinct "Auto-freigegeben" badge (`AgenticStatusCard`, `agenticStatusLabels`, `StatsCard` pie). Config flag defaults **off** so enabling it is a deliberate operator choice. Tests: `result-handler-auto-approve.test.ts` (gate on/off), `auto-approve-erp-eligibility.test.ts` (export inclusion).
**Why (operator decision):** Auto-approved items flow to ERP without a mandatory human touch — the operator chose eligibility (sort-by-state + decide what to sync) over a second gate, since the sync itself is already a deliberate action.
**Deferred:** No auto-reject counterpart (only auto-approve). Confidence threshold is a single global value, not per-subcategory. No dedicated "promote auto_approved → approved" bulk action (uses existing Abschliessen). Gate integration relies on env read at config load; a per-request override is not exposed.

## 891. ✅ Disambiguate `cancelled` vs `failed`: user-cancel vs pipeline error (+ reason in UI)
**Why:** `cancelled` was overloaded — it meant both an explicit operator stop AND a run that errored and exhausted its 5 auto-retries; worse, exhausted invocation errors terminated in `cancelled` while stale/over-cap errors terminated in `failed`, so an errored run masqueraded as a user cancel (neutral "Abgebrochen" badge).
