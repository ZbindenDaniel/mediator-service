## 926. ✅ Review reworked into an edit-in-place wizard with an end-of-flow decision
**Why:** The review flow's content steps were Ja/Nein-only, so a minor problem forced a full *Nein* → reject → re-run for a one-value fix, and mixing per-step pass/reject with inline editing was confusing. Reworked the whole flow into a single `AgenticReviewWizard` component (new file): the reviewer walks Artikelbeschreibung → Kurztext → Spezifikationen → **Dimensionen** → Preis with **Zurück/Weiter**, each step edit-in-place (text/number inputs; specs are the coalesced contract + Langtext fields, blank = remove) plus an **always-present feedback box**. The **approve/reject decision moved to the end**: a **summary** step recaps every value + collected notes and offers **Ablehnen** / **Freigeben**; the **Shop step is shown only after Freigeben** (per operator request: decide, then publish). Back-navigation required a single stateful modal rather than the previous chain of independent dialogs. The wizard returns one result — `{ decision, referenceEdits, specValues, reviewPrice, shopArticle, notes }`; `ItemDetail.promptAgenticReviewInput` now preps the field data, opens the wizard once, and maps the result. The explicit decision is sent as `decision` in the review payload (backend already honors `data.decision` over checklist-derived signals). Edits ride `referenceEdits` → `applyReferenceEditsAfterReview` writes them to `item_refs` **on approval only**; the whitelist is typed — text (`Artikelbeschreibung`/`Kurzbeschreibung`) + numeric (`Länge_mm`/`Breite_mm`/`Höhe_mm`/`Gewicht_kg`, comma-decimals, coerced). Per-step notes are tagged (`"Dimensionen: …"`) and concatenated into the run `notes`.
**Why the wizard (vs. the earlier per-step Passt/Problem modal):** operators wanted to make notes and edits across all steps first, then make one informed approve/reject decision with a summary in front of them — not decide field-by-field. Zurück/Weiter needs shared state across steps, which a chained-dialog approach can't give.
**Deferred:** The structured checklist flags (`bad_format`, `wrong_physical_dimensions`, `information_present`) are **not** set by the reviewer anymore — they're sent at their non-blocking defaults and the explicit `decision` drives approve/reject. Deriving those flags from the wizard inputs (edits made + notes) is an open decision (todo, operator wants to think about it); until then per-flag review **metrics** will read as all-positive. Edits on a rejected run are not persisted (consistent with `specValues`). The now-unused per-step/contract review modals (`AgenticStepReviewModal`, `AgenticContractFieldReviewModal`) and their `ItemDetail` plumbing are left in place for now (the rework/"KI Überarbeitung" path still uses `AgenticSpecFieldReviewModal`).

## 925. ✅ Hard-drive dimensions fall back to standard 2.5″/3.5″ form factors (via a new spec contract)
**Why:** For hard drives and SSDs, exact physical measurements are rarely published, so web search usually returns nothing and the extraction left `Länge_mm`/`Breite_mm`/`Höhe_mm` blank — yet these drives are almost always one of two standard form factors. The pipeline already supports per-subcategory `guidance` (`contracts/specs/<code>.json`, injected into the `{{EXTRACTION_REVIEW}}`/`{{SUPERVISOR_REVIEW}}` placeholders by `item-flow-extraction.ts`), but **no spec contract existed for drives** — subcategory **901** (Festplatte) / **905** (Externe Festplatte) had no `contracts/specs/*.json`, confirmed against the repo (drives were only referenced as `targetSubcategory: 901` in the laptop/desktop *assembly* contracts). Added `901.json` and `905.json`, each with a real field set (Speichertyp/Speicher/Formfaktor/Schnittstelle/Drehzahl for 901; +Stromversorgung for 905) plus a `guidance` entry: 901 tells the agent to fill dimensions from the form factor when sources are silent (**2.5″ → 100×70×7 mm**, Höhe 9.5/15 for thicker drives; **3.5″ → 147×102×26 mm**); 905 leaves total dimensions to the enclosure (they vary), only filling when the source states them.
**Why a contract, not the general prompt:** keeps the hint category-scoped and operator-editable through the existing guidance mechanism (README's own worked example is literally HDD dimensions), instead of hard-coding a drive-only rule into `extract.md` that every category's extraction would carry. Bonus: because a spec contract now exists for drives, the review flow's step-3 uses the editable contract-field modal for them, and the drive fields join `getFilterableSpecKeys()` for Shopware.
**Deferred:** No `version` bump beyond the initial `1` — guidance is advisory and doesn't force an idle re-enrich sweep of existing drives. The fallback fires only when the form factor is stated/determinable; no blind default is assumed. The supervisor's existing plausibility check still applies.

## 924. ✅ Creating an instance of an existing reference no longer restarts an approved/in-review run
**Why:** When an operator created another instance of an existing `item_ref` (via ItemCreate match-selection, or intake-complete), the agentic pipeline was re-triggered even though the reference already had an `approved`/`review` run — wiping a completed result or clobbering a run awaiting human review. Root cause: `import-item` correctly declines to re-seed when a run exists (`hasExistingAgenticRun` guard), so it returns `agenticTriggerDispatched:false`; the frontend then fires its own client-side trigger to `POST /api/agentic/run`. `forwardAgenticTrigger`'s "already-exists" branch only treated `queued`/`running` (`AGENTIC_RUN_ACTIVE_STATUSES`) as "leave it alone" and **restarted every other status** — including `review`, `approved`, `auto_approved`. Enrichment is shared at the Artikel_Nummer level (specs sync across all instances), so a new instance needs no fresh run. Fix: `forwardAgenticTrigger` now restarts only a `notStarted` run from this automatic path; any active/settled run (`review`, `approved`, `auto_approved`, `rejected`, `failed`, `cancelled`, or already active) is returned untouched with `200`. Explicit operator restarts are unaffected — they go through the dedicated `POST …/agentic/restart` endpoint (`restartAgenticRun`), which sets `queued` directly.
**Deferred:** Bulk "KI starten" (`item-list-bulk`) and the ItemDetail start button share this choke point, so they too now start only `notStarted` runs and skip settled ones instead of restarting them — a deliberate, safer alignment with the repo's "failures are terminal, restart is explicit" design (agentic README / #913); a dedicated bulk-restart affordance for `failed` runs was not added. No change to `import-item`'s own guards (already correct).

## 923. ✅ Operator can delete a stored search-result link so bad results stop poisoning the pipeline
**Why:** #916 surfaced the stored search evidence (`agentic_runs.LastSearchLinksJson`) in the KI tab as a read-only `Suchergebnisse (N)` list, but a bad hit stayed in the blob and kept feeding the reuse/grounding path — a skipped-search rerun (`skipSearch`) reads that blob back verbatim as authoritative evidence (#921), and the extraction context is built from it. The next logical step (todo #21, and the #916 follow-up "source **curation** — pin/remove") is to let operators remove a link. Implemented as a **targeted prune**, deliberately distinct from `deleteAgenticRun`: removing one link must **not** reset the run's status/review — only the offending source disappears.
- **Backend service `removeAgenticSearchLink`** (`backend/agentic/index.ts`): resolves the Artikel_Nummer, loads the run, parses `LastSearchLinksJson` with a defensive parser (mirrors the frontend `parseAgenticSearchSources` + result-handler `normalizeSearchLinks` — a malformed blob degrades to `[]` rather than throwing), filters out entries whose `url` matches, and persists the remainder. An emptied list persists as **`null`** (same shape as a never-searched run) so downstream reuse/grounding treats it as "no evidence" rather than an empty-array edge case. Declines with `not-found` (no run), `link-not-found` (url absent), or `missing-url`/`missing-actor`. Logs an `AgenticSearchLinkRemoved` event (level `important`, topic `agentic`).
- **Persistence via `updateAgenticRunStatus`, not a bespoke UPDATE:** that helper is already in the action ctx/deps, but it rewrites `Status`/`LastModified`/`ReviewState` unconditionally — so the service echoes the run's *current* Status/ReviewState back and flips only `LastSearchLinksJsonIsSet`, leaving everything else untouched. This avoided threading the existing `persistAgenticSearchLinks(db)` helper into the action ctx + `AgenticServiceDependencies` (extra wiring surface for no behavioral gain).
- **HTTP action** `agentic-search-link-delete.ts` → `POST /api/item(-ref)s/:id/agentic/search-links/delete` (`{actor,url}`), auto-registered by the folder loader, modeled on `agentic-delete.ts`. Route is non-overlapping with the `/agentic$`, `/agentic/delete$`, and `/agentic/(review|close)$` matchers.
- **Frontend:** `persistAgenticSearchLinkDeletion` in `lib/agentic.ts` returns the refreshed run; `AgenticSearchSources` gained an optional `onDelete`/`deletingUrl`/`disabled` set and renders a per-row `×` remove control; `ItemDetail.handleAgenticSearchLinkDelete` confirms, calls the endpoint, and swaps in the returned run so the list re-renders with no full status refetch. Removal is disabled while any other agentic action is pending.
**Deferred:** Pin/reorder and **adding** a manual link (the other half of #21/#22 curation, which feeds a structured `WebLinks` field on ItemRef) — this change is removal-only. No undo (the event log records the removal; a re-run re-populates evidence). URL match is exact-string (the stored shape is a single canonical url per entry); no normalization/dedupe pass. `condenseSearchText`/reuse consume the pruned blob on the next run — no immediate re-extraction is triggered by a removal.

## 922. ✅ Fix "most/all agentic runs fail with EXTRACTION_FAILED" (empty completions) + context bounding + traceability
**Why:** Production log — nearly every run terminated `EXTRACTION_FAILED` with `lastValidationIssues: null`, `itemContentPreview: ''`, and per-attempt `json match missing. Trying again`. That signature means the extraction model returned an **empty** (or JSON-free) completion on every attempt: the `jsonMatch = itemContent.match(/\{[\s\S]*\}/)` at `item-flow-extraction.ts` found no `{…}`, took the `advanceAttempt(); continue` branch **without** setting `lastValidationIssues`, so after `maxAttempts` the terminal error fell through to the catch-all `EXTRACTION_FAILED` with a null reason. Two compounding root causes:
- **No Ollama `num_ctx`.** `invoker.ts`'s `ChatOllama` was built with only `baseUrl`/`model`/`keepAlive` — no `numCtx` — so Ollama used its **default 2048-token** window. The extraction prompt in the log was `promptLength: 21961` (~6-7k tokens), ~3× the window; Ollama silently left-truncates the overflow (dropping the system prompt + "return JSON" instructions) and commonly emits an empty completion. (This is the long-suspected todo #0-1 "categorizer empty-completion = context overflow" hypothesis, now confirmed and hitting extraction, whose prompt is the largest stage.)
- **Extraction was fed the raw, unbounded context.** The operator spotted that the one run that *succeeded* had tiny search input. Confirmed in code: extraction uses `searchContexts[contextCursor].text` **raw** (`singleContextLength: 16502` for the failing "Apple Keyboard M0118"), while the categorizer gets `buildAggregatedSearchText()` — which runs `sanitizeSourceText` (3-paragraph cap, boilerplate/URL stripping) and shrank the *same* item to 242 chars. So the sanitizer that protects the categorizer never ran on the extraction context; big items overflowed, small ones squeaked through.

Fixes (layered — primary control + safety net + observability):
- **`num_ctx` (primary).** New `MODEL_NUM_CTX` (default **8192**) + optional `MODEL_FORMAT_JSON` (`format: "json"`, default **off** — it suppresses a reasoning model's `<think>` phase, which the extraction path handles) threaded through `config.ts` `modelConfig` and applied to the `ChatOllama` client (spread conditionally; the options object is already cast to the constructor params so the fields type-check regardless of published typings). A `loaded ollama chat model` info log records the effective `numCtx`/`formatJson`.
- **Deterministic context condensation (`condenseSearchText`, safety net; operator chose this over an LLM summarize stage).** New `utils/search-condense.ts` keeps **spec-bearing lines** (numbers+units, model codes, price/article keywords — same heuristic as `sanitizeSourceText`) and drops boilerplate/nav/duplicate/URL-noise lines, filling a 12k-char budget **spec-lines-first** rather than blindly truncating — so quality is preserved (a spec line at the *end* of a page survives a head-cut). Small contexts (already under budget) pass through **verbatim**, so well-sized items behave exactly as before. Guarantees output ≤ budget, and never returns empty for non-empty input (an oversized single line is sliced, not dropped — an empty context would just re-trigger the no-JSON failure). Wired into the extraction context build, replacing the raw `activeContext.text`.
- **Traceability.** The blind `json match missing` **debug** line is now a **warn** logging `rawLength` / `hadThinkBlock` / `strippedLength` / `rawSnippet` — so "empty (overflow)" vs "reasoning-only `<think>`" vs "prose, no JSON" is distinguishable at a glance — and it now records `lastValidationIssues = passFailureValidationIssues = 'EMPTY_OR_NO_JSON'`, so the terminal `EXTRACTION_FAILED` log carries a real reason instead of `null`. `condenseSearchText` also emits a `condensed extraction search context` warn with kept/dropped/spec counts.
**Why (approach):** `num_ctx` is the real fix (the prompt actually *fits* 8192); condensation is defense-in-depth so a pathologically large multi-source blob can't overflow regardless of the window, and it was chosen deterministic (no LLM) because raw Tavily text is mostly nav/marketing — a spec-line ranker recovers most of the signal at zero per-run cost and adds no new failure surface (an LLM summarizer would itself need chunking to avoid the very overflow being fixed). Left `sanitizeSourceText`/`buildAggregatedSearchText` (the categorizer path) untouched to avoid perturbing its tests — added a *separate* condenser for extraction. Kept the thrown error code `EXTRACTION_FAILED` (only the logged reason gained specificity) so downstream status/UI mapping is unchanged.
**Deferred:** The optional **LLM summarize/condense stage** (map-reduce distill, per the design discussion) is not built — revisit only if the new telemetry shows deterministic condensation still loses signal on real items. The 12k-char extraction budget is a module constant (not env-exposed) — `num_ctx` is the intended knob. `MODEL_FORMAT_JSON` is a global on/off, not per-stage. Full `tsc`/jest not run in this environment (fresh clone, no `node_modules`); the condenser's logic was validated via a standalone harness (5 cases incl. the oversized-single-line guard) and `search-condense.test.ts` was added for CI.

## 921. ✅ Skip-search reuses collected results as real evidence, not just a "search skipped" note
**Why:** Report from a transcript — a skipped run's extraction prompt showed `Reviewer: Search skipped per reviewer request. Minimize new searches.` followed by a `Current search context:` that carried no actual results, i.e. the model was effectively told only that search was skipped. Root cause is in the reuse path (`item-flow-search.ts`, `!shouldSearch` branch): it built the injected context by joining **only** each stored source's `description`/`content`. The persisted `LastSearchLinksJson` shape is `{url, title?, description?}` and very often has **no** `description` (Tavily returned title+url without a snippet), so the join produced an empty string; the extraction then rendered `Current search context: None.` even though non-empty stored sources existed and were passed in. Fix: format stored sources with the shared `formatSourcesForRetry` (numbered `Title` / `URL` / `Description: (none)` blocks) so titles + URLs always carry evidence and the block is **never empty when sources exist**; and in `item-flow-extraction.ts` relabel the block, when search is skipped and the context is non-empty, to `Previously collected search results (search skipped — extract from these; do not assume no evidence):` so the model treats the reused sources as authoritative rather than assuming there is nothing to work from.
**Why (approach):** Reused the existing `formatSourcesForRetry` (already the format the in-cycle retry path uses for sources) instead of inventing a second serialization — one attribution format for "here are the sources," whether fresh-retry or reused-skip. No schema/flow-shape change: still one `SearchContext` pushed with the same `sources` array; only its `text` rendering and the extraction label changed. Guarded the label switch on `singleContextText` being non-empty so a genuinely empty context still reads `Current search context: None.`. Test: new `item-flow-search.test.ts` case asserts the skip path yields a single non-empty context containing the title + URL of a **description-less** stored source (the previously-collapsing case) plus a described one.
**Deferred:** No sanitization of the reused block through `buildAggregatedSearchText`'s URL/whitespace trimmer — the skip path stores raw formatted text (same as before; the formatter output is already compact). No change to how many stored sources are reused (still the full persisted set, capped at persist time). The empty-description root cause upstream (why some sources persist with no snippet) is unchanged — this makes the reuse robust to it rather than backfilling descriptions.

## 920. ✅ Abbrechen silently no-op'd on non-numeric references (leftover numeric guard)
**Why:** `persistAgenticRunCancellation` still carried the `trimmedArtikelNummer.startsWith('I-') || !/^\d+$/.test(trimmedArtikelNummer)` guard — the same numeric-only client guard that was already identified and removed from `persistAgenticRunClose` (#876, "silently rejected every real Artikel_Nummer and broke Abschliessen"). Investigated the reported "cannot delete agentic runs" alongside this: the delete/reset path (`persistAgenticRunDeletion` → `agentic-delete` action → `deleteAgenticRun`) has **no** such guard, is wired end-to-end (`ItemKiTab` Löschen button → `handleAgenticDelete`), routes uniquely, unit-tests green, and typechecks — its "make deletion stick" `SearchQuery`-clear fix already shipped in #876, so no code defect remained there in the current tree; the surviving silent-no-op in the KI-run action client was this cancel guard.
**Deferred:** No behavior change to the delete semantics (it deliberately resets a run to `notStarted` and preserves protocols rather than hard-deleting the row) — if operators want a true purge that's a separate decision. The other agentic action clients (`persistAgenticRunClose`, restart payload builder) carry no numeric guard and were left as-is.
## 919. ✅ Fix queued agentic runs being promoted to running then cancelled instead of waiting
**Why:** Report — "queued runs get moved to running and then cancelled immediately; they should wait until there is space." Root cause is a lost invariant, not a single bad line. In the original design (`e3a559f`) the queued→running promotion re-counted running runs **inside its own transaction** and refused to promote (leaving the run `queued` to wait) when `MAX_CONCURRENT_RUNNING_RUNS` was already reached — an atomic, self-correcting cap. Commit `499d8a4` ("Multi-instance agentic safety") moved the promotion up into `claimQueuedAgenticRuns` (atomic `FOR UPDATE SKIP LOCKED`) and **removed that per-invocation count-gate**, reducing `runInBackground`'s guard to "is this row still `running`". Cap enforcement then rested entirely on the dispatcher computing `availableSlots = MAX − runningCount` and claiming that many. That read-then-claim is **not atomic across dispatch invocations**, and the dispatch loop is a bare `setInterval(dispatchQueuedRuns, 5000)` with **no reentrancy guard** (`server.ts`) firing a `void`-ed async tick. When a tick's DB work outlasts the 5 s interval (stale-run sweep + over-cap sweep + counts + feeder, under load), the next firing overlaps it: both ticks read the same low `runningCount`, both call `claimQueuedAgenticRuns`, and — because `SKIP LOCKED` only stops claiming the *same* row, not *additional* rows — together they promote more than the cap into `running`. The over-cap safety net at the top of the next tick then saw `> MAX` running and flipped the excess to terminal `failed` (`over-cap-cancelled`), which surfaced exactly as "a just-queued run went running then cancelled." Three-layer fix, smallest-blast-radius first:
- **Reentrancy guard (`server.ts`):** a `dispatchInFlight` flag skips a firing while the previous `dispatchQueuedAgenticRuns` promise is still settling, so ticks serialize and each claim sees the previous tick's committed promotions. This alone closes the single-instance trigger (the deployment is single-instance).
- **Cap-aware claim (`db.ts` `claimQueuedAgenticRuns(limit, maxRunning?)`):** an optional running-cap arg clamps the claim `LIMIT` to `LEAST(limit, GREATEST(0, cap − (SELECT COUNT(*) running)))` computed **in the same statement** as the promotion, so the claim itself can never move more than the free slots into `running`. The dispatcher passes `MAX_CONCURRENT_RUNNING_RUNS`; omitting the arg preserves the old limit-only behavior. This restores, at the claim layer, the guarantee the deleted count-gate used to provide.
- **Over-cap → requeue, not fail (`index.ts`):** if the sweep ever still finds `> MAX` running (a residual race, a restart, manual DB edits), it now pushes the excess back to `queued` so they **wait** for a slot, instead of failing them. It keeps the runs with the **oldest** `LastAttemptAt` running (those are the ones actually progressing in a background invocation) and requeues the freshest excess (a racing over-claim stamps `LastAttemptAt = now`); `ORDER BY … ASC OFFSET MAX`. `RetryCount` is preserved and `LastError` cleared (requeue is not an attempt/failure), and no `AgenticRunFailed` event is emitted for a requeue. A requeued run whose background invocation is still mid-flight is safe: that task's promotion guard re-reads `Status` and bails when it is no longer `running`.
**Why (approach):** The three layers are ordered by blast radius — the guard is the actual fix for the observed single-instance case; the cap-aware claim hardens the primitive so any future overlap/instance can't over-fill; the requeue makes the last-resort sweep honor the user's stated intent ("wait, don't cancel") for any excess that still slips through. Kept `MAX_CONCURRENT_RUNNING_RUNS` as the single knob and reused the existing `updateQueuedAgenticRunQueueState` path (no schema change). Tests: `dispatch-queue-concurrency.test.ts` updated for the new claim arg and a new case asserting over-cap requeues (not fails) while preserving `RetryCount`.
**Deferred:** No Postgres advisory lock for a truly serializable multi-instance claim — the cap-aware `COUNT` subquery narrows but does not fully eliminate the multi-instance over-claim window (two instances can both read `running=0` before either commits); acceptable because the deployment is single-instance and the requeue-not-fail net now makes even a residual over-claim wait rather than die. `over-cap-cancelled` as a terminal reason is retired for the running-slot case; `recordQueueTerminalTransition` stays for the genuine `stale-run-auto-cancelled` / `missing-search-query` terminals. Stale-run recovery (10-min zombie reclaim) is unchanged.

## 918. ✅ AI-runs phase 4: run snapshots + KI-tab diff + non-destructive restore (Thread 4)
**Why:** Operators had no way to see what a run changed or to undo a bad run/rework — a failed rework could even demote an already-good item. This adds **version history for the AI-enriched state**: full snapshots (chosen over deltas/temporal tables — a bounded field set a human needs to eyeball and roll back), captured **before** each run mutates the item, so the newest live item is the current state and each snapshot is both a diff anchor and a rollback point. Decisions (with the operator): snapshot-before-run timeline; **manual** restore; retention **keep 4 recent + always the last approved state**; restore is **non-destructive** (writes a new `restore` snapshot); field set = what the AI writes (instance/intake fields deferred). Pieces:
- **Schema (`db.ts`):** new `agentic_run_snapshots` table (`Id, Artikel_Nummer, RunId, CreatedAt, Reason ('pre-run'|'pre-rework'|'restore'), CapturedReviewState, Actor, TriggerReason, SchemaVersion, FieldsJson`), additive `CREATE TABLE IF NOT EXISTS` in the first init batch. Helpers `insertAgenticRunSnapshot`, `listAgenticRunSnapshots`, `getAgenticRunSnapshotById`, and `pruneAgenticRunSnapshots` (deletes all but the 4 newest **plus** the most recent `approved`/`auto_approved` snapshot, so an item can always be rolled back to its last known-good state even if it scrolled past the window).
- **Capture (`invoker.ts`):** before the request-payload merge / Artikelbeschreibung fill-in, snapshot the pure DB fields (`buildSnapshotFields` — the 13 AI-written keys incl. `Langtext`) with the run's current `ReviewState` (for the approved-retention rule) and Reason (`pre-rework` when `reworkSpecFields` is set, else `pre-run`). Best-effort: a snapshot failure never blocks the run.
- **API (`actions/agentic-snapshots.ts`, auto-registered):** `GET /api/item-refs/:artikel/agentic/snapshots` lists newest-first; `POST …/snapshots/:id/restore` overlays the snapshot's fields onto the item ref (`persistItemReference`, preserving all non-snapshot fields), records a new `restore` snapshot, prunes, and logs an `AgenticSnapshotRestored` event.
- **UI (`AgenticSnapshotsPanel.tsx` in the KI tab):** a "KI-Verlauf" timeline (timestamp, reason, captured review state) with a **field-level diff** of the selected version → current item (`computeSnapshotDiff` — top-level fields by display value, `Langtext` key-by-key, only changed fields), and a confirmed "Wiederherstellen" button per version. `ItemDetail` passes the current fields (Langtext parsed to match the snapshot shape) and refreshes on restore.
**Why (approach):** Snapshot-before-run gives the diff *and* the rollback source from one mechanism; the pre-mutation capture is a guaranteed-clean restore point even if a run half-writes then fails. Restore-as-new-version (git-revert semantics, not reset) preserves the audit trail. Retention keeps the last approved beyond the window because that is exactly the state you want to roll back to. Diff is computed on structured JSON (not text) so `Langtext` spec changes read clearly. Provenance (actor, trigger reason, run id, captured review state) is stored so a diff answers *who/why*, not just *what*.
**Deferred:** Instance/intake fields (`InstanceSpecs`, serial/MAC) are out of scope — flagged for their own history later (operator noted it will be needed). No auto-restore on failure (manual only, by choice). Snapshot capture is per-run-start only (no separate post-approval capture — the approved state is preserved via the pre-run snapshot of the next run + the retention rule). Backend DB helpers aren't unit-tested here (need a live Postgres; the repo's mock-based action tests are skipped under the custom harness) — the pure `computeSnapshotDiff` is covered by `AgenticSnapshotsPanel.diff.test.tsx`.

## 917. ✅ AI-runs phase 3: identity grounding so a confused search can't flip the device class (Thread 1/3)
**Why:** A misleading `Artikelbeschreibung` sent the search off the rails and extraction then *confidently* rewrote the item to match the off-topic sources (the "PC catalogued as a Pokémon card set" failure). Two root causes in the prompt path: the model was handed category **codes** buried in the target JSON (never the device class in human terms), and `extract.md` explicitly instructed *"Correct Artikelbeschreibung to the precise product name stated in sources"* — an open licence to change the device class. Per the operator's steer, no new schema: the run's `agentic_runs.SearchQuery` already carries a stable identity anchor the pipeline does not overwrite mid-run, so grounding is purely prompt-side. `buildIdentityGroundingFragment` (`item-flow-extraction.ts`) composes a short ground-truth instruction from the anchor (`searchTerm`, falling back to the original `Artikelbeschreibung`) + the known subcategory **label** (resolved via `getSubcategoryLabelFromCode`), and injects it — FIRST, ahead of reviewer notes and category guidance — into the extraction and supervisor review placeholders (`appendPlaceholderFragment`), mirroring the #910 category-guidance path. Not injected into the categorizer (which decides the category itself, so grounding it on the prior category would bias it). `extract.md`'s Artikelbeschreibung rule was reworded to "refine the product name only WITHIN the known device class; never change the device class — if sources describe a different kind of product, keep the provided value." Threaded `searchTerm` from `runItemFlow` into `runExtractionAttempts`. New test in `item-flow-trigger-fragments.test.ts`; `prompt-template-composition` snapshot updated for the reworded rule.
**Why (approach):** The fragment is injected via the existing placeholder mechanism rather than a new prompt token, so it composes with the reviewer-notes/guidance/signal fragments already there and needs no template surgery. Extraction + supervisor (enforcement) only — deliberately excluding the categorizer keeps the #910 boundary ("categorizer decides category, not content"). Best-effort: when neither an anchor nor a resolvable label exists the fragment is `null` and nothing is injected — grounding never becomes a hard gate that could block a run. ## 913. ✅ Harden the agentic auto-dispatcher (demote keep-busy, kill switch, terminal failures, transient retries)
**Why:** Incident — the auto-dispatcher burned ~1000 search queries in minutes and revived runs the operator had stopped ("no matter how many I stop there's always a few waiting"). Root causes were compounded in the keep-busy path added in #908/#909: (a) `claimIdleFillAgenticRuns` reset `RetryCount = 0` on every claim, defeating the `MAX_AUTO_RETRIES` ceiling so a permanently-failing item retried forever; (b) it claimed `failed`/`cancelled` runs, so an operator `cancelled` (and an auto-`failed`) run was auto-resurrected — a human stop was not durable; (c) the #909 "searches at most once" invariant was false for the failing items, because `collectSearchContexts` threw on the *first* failed plan **before** `persistSearchLinks` ran, so a failed search never persisted links and every retry re-billed the provider. Fast-failing Tavily errors (`200 Error: undefined`) + 3 slots + a 5s tick + no ceiling produced the burst.

Per the operator's direction the auto-dispatcher was **demoted to a `notStarted`-only feeder**, and failures made terminal. Changes:
- **DB (`db.ts`):** replaced `claimIdleFillAgenticRuns` with **`claimNotStartedAgenticRuns`** — promotes only `notStarted` → `queued` (never `failed`/`cancelled`), `FOR UPDATE SKIP LOCKED`, and does **not** touch `RetryCount`/`LastAttemptAt` (promotion to the waiting queue is not an attempt).
- **Dispatcher (`index.ts`):** the feeder now tops up the **waiting** queue up to `MAX_WAITING_RUNS` (= `MAX_CONCURRENT_RUNNING_RUNS`, so ≤ N running + N waiting) and no longer promotes straight to running or invokes the model — the normal `queued → running` claim drains it on a later tick. The feeder still runs when all running slots are busy (so the waiting buffer stays full). `autoCancelAfterFailure` and the stale-run sweep now land in **terminal `FAILED`** (no auto-requeue/backoff); the `MAX_AUTO_RETRIES`/`RETRY_BACKOFF_MINUTES` constants are gone. Added an admin kill switch `agentic_auto_dispatch_enabled` (default ON when unset) read via `getSystemSetting`; when off, the feeder (and the idle contract-audit sweep) are skipped while explicit user-triggered runs still dispatch.
- **Kill switch UI:** `admin-agentic-dispatch.ts` (GET/POST `/api/admin/agentic-dispatch`, admin-auth) + `AgenticDispatchCard.tsx` on the Admin page, mirroring the Nightly-ERP-Sync toggle.
- **In-process resilience** (the safety net that makes "failed = terminal" acceptable): Tavily client (`tavily-client.ts`) retries transient failures (timeouts, 5xx, the malformed-2xx `200 Error` anomaly) with backoff and passes a shorter per-request `timeout` (20s) so a hung request fails fast; 4xx/429 are not retried (429 still surfaces as `RateLimitError`). `collectSearchContexts` is now **per-plan tolerant** — one plan's transient failure no longer aborts the run; it fails only if *every* plan failed, so partial results survive and get persisted for a search-free retry. The Ollama client (`invoker.ts`) sets `keepAlive` to keep the model resident and wraps `invoke` in a transient retry (targets undici `UND_ERR_HEADERS_TIMEOUT` on cold model load).
**Why (approach):** The operator explicitly scoped the auto-dispatcher down to "feed unstarted runs, full stop — all other states have a reason to be idle." Making `failed`/`cancelled` ineligible for auto-claim (rather than adding more cooldown/ceiling logic on top of #909) is what makes an operator stop durable and stops the resurrection loop at the source. Terminal failures + in-process retries move recovery *inside* a run (bounded, no re-billing storm) instead of resurrecting whole runs through the dispatcher. The kill switch reuses the existing `system_settings` + admin-card pattern, so it needed no new storage or auth. Capping waiting with the same `MAX_CONCURRENT_RUNNING_RUNS` parameter keeps configuration to one knob.
**Deferred:** The kill switch scopes to the auto-feeder only (explicit triggers still run) — no global emergency-stop of the whole dispatch loop. Failed runs now require a manual re-trigger (no automatic recovery); this is intentional. `MAX_WAITING_RUNS` is hardwired to the running cap rather than separately configurable. The Ollama undici header timeout is mitigated via `keepAlive` + retry rather than a custom dispatcher `headersTimeout`, since LangChain's `ChatOllama` does not cleanly expose one. Tavily's `timeout` option is passed best-effort (ignored by SDK versions that don't support it; the retry still bounds latency).

**Why:** Follow-up to #908. Most runs settle as `failed` or `cancelled`, and the operator wants those retried automatically — but the reason not to before was the search-token burn. ## 908. ✅ Fix agentic search-token burn: atomically claim idle-fill ("keep-busy") runs
**Why:** Report — "the automatic dispatcher starts over and over again and we burn all our search tokens with the same search queries." Root cause is the idle-fill/keep-busy branch of `dispatchQueuedAgenticRuns` (runs every 5 s). Bulk imports deliberately create runs as `notStarted` **with a `SearchQuery`** so they don't flood the queue (`import-item.ts`: *"keep-busy picks them up when a slot is free"*). The queued path claims those atomically — `claimQueuedAgenticRuns` flips `queued → running` in a single `FOR UPDATE SKIP LOCKED` statement so a run is dispatched exactly once — but idle-fill used a **plain, non-atomic `SELECT`** (`fetchIdleFillAgenticRuns`) that never transitioned the run out of the `notStarted`/selectable state. So the same `notStarted`+`SearchQuery` rows were re-selected and re-dispatched on every tick, re-billing the identical Tavily search queries. The mismatch compounded with `scheduleAgenticModelInvocation`'s promotion guard (`Status === 'running'`, written to match the atomically-claimed queued path): a `notStarted` idle-fill run could never satisfy it, so it never left `notStarted` and the busy-loop was permanent. Fix: renamed `fetchIdleFillAgenticRuns` → **`claimIdleFillAgenticRuns`** and rewrote it to mirror `claimQueuedAgenticRuns` — a `WITH … FOR UPDATE SKIP LOCKED` CTE that flips eligible `notStarted` rows to `running` (stamping `LastAttemptAt`, clearing `NextRetryAt`/`LastError`) and `RETURNING agentic_runs.*`. Each keep-busy run is now claimed exactly once (no re-selection ⇒ no repeat search), and because it is already `running` the promotion re-check passes, so keep-busy actually executes. Concurrency math is unchanged: idle-fill still claims at most `remainingSlots = MAX − running − scheduled − 1` (the reserved slot keeps an explicit trigger able to start immediately), so a cycle never exceeds `MAX_CONCURRENT_RUNNING_RUNS`. Retry/terminal semantics are unchanged: a failed idle-fill run requeues to `queued` with its `RetryCount` (bounded to `MAX_AUTO_RETRIES`), and a stuck `running` run is still recovered by the stale-run sweep. New regression test in `dispatch-queue-concurrency.test.ts` asserts the claim limit (reserving 1 slot) and that a claimed run invokes the model exactly once.
**Why (approach):** Reused the existing, proven `claimQueuedAgenticRuns` atomic-claim pattern rather than inventing a new dedup mechanism or relaxing the promotion guard — a plain SELECT + a `running`-only guard is exactly the inconsistency that caused the burn, and the single-claim invariant is what prevents re-billing. Claiming straight to `running` (vs. to `queued`) keeps dispatch immediate and matches the guard's documented expectation that a run reaching `scheduleAgenticModelInvocation` is already claimed.
**Deferred:** `notStarted` runs are still resumed only by the live dispatcher, not by `resumeStaleAgenticRuns` on startup (which handles only `queued`/`running`) — unchanged. Entry 876 only cleared `SearchQuery` on the delete path to stop that one re-promotion trigger; this addresses the general mechanism, so the delete-time clear is now belt-and-suspenders rather than the sole guard.
